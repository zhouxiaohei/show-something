背景与难点

文档写全了，协作仍然会出错：四个难点

一个团队把排障经验、架构说明、操作规则整理进仓库，文件齐全、链接检查通过。编码 Agent 接入后，局面却是：资料明明存在，它仍沿用旧规则；某次纠正后答对，换个任务又漏掉限制；代码已更新，旧教程依然提供看似完整的答案。人又开始充当资料路由器与版本裁判。要检查的问题是：我们维护的是一堆可以被阅读的文件，还是一套能让使用者取得适用知识的系统？

四个难点：同一知识点要支持查询、理解、决策三种阅读任务；文档正本不天然等于当前事实，不同问题的依据不同；保存了知识不代表本次任务取得并用对——只检查最终答案，无法知道该修正文、导航、表达还是判据；一次策略调整会跨越代码、文档和多个项目，需要回答谁负责更新、什么变化触发复核。

解决思路

把"知识归属、消费方式、使用验证、变更责任"分开设计

四个目标对应四个难点：一个重要事实由谁维护、依据在哪里；不同任务怎样取得它；怎样判断本次使用是否有据；它变化以后哪些对象需要复核。这不是四个先后步骤，是长期并存的职责。

三种更直接的办法各有代价：把全部文档一次性交给 Agent，把相关性、历史版本与适用条件的筛选留给本次上下文，不解决来源过期；分别维护人版和模型版全文，变更就要同步两次，易变事实仍应有正本；只要求"先读文档"再用答题分数验收，既没说明哪些问题必须追溯什么依据，也没区分事实已过期与模型没用对。

本文采用的思路：单一知识归属，多种消费入口，分开检查对象，按依赖维护变化。代价是需要维护导航、范围、关键检查与责任记录；收益应通过真实使用观察，而不是靠目录结构本身宣布成立。

总体方案

四部分怎样组成一个整体：谁保存依据，谁组织入口，谁发现问题，谁推动修订

四部分是文档体系的职责划分，不要求部署四个独立服务，也不要求建立四套文件夹。同一文件可能承担不止一种职责，关键是每项知识的归属与依赖清楚。

用导出问题看配合：J17 该不该取消，正本负责说明适用策略；导航指出查找条件与入口；使用验证检查实际读取片段和建议能否支持这个决定；发现只读了旧版本，维护负责修入口、范围标识或文档内容。如果实际生产策略已经改变，问题从事实依据一侧进入，而不是等 Agent 答错以后才开始处理。

知识正本

事实、解释与运行观察分别归谁：文档不能自己任命自己为真相

一篇文档把等待时间写成 60 秒、另外五篇都链接它，满足了单一正本，却不保证生产真的按 60 秒运行。要分开两层：事实依据回答"为什么认为这件事成立"（代码与测试、环境证据、负责人确认）；文档正本回答"团队在什么位置维护对这件事的说明"。一个重要事实至少要让读者追到四件事：说什么对象、适用什么范围、依据在哪里、谁负责复核。

同一项目的知识分工：执行时必须遵守的规则放精简的项目指令入口；项目事实与操作策略放有维护者的项目文档，按任务读取；设计解释与历史经验放决策记录与复盘；个人偏好与临时记录放个人配置，不自动升级成团队项目事实。反例："等待上限改成 60 秒"靠私人记忆维持，换个协作者就丢。

阅读与导航

单写多视图，再把资料送到实际任务中

两类读者其实是两种阅读任务：查等待上限时人和 Agent 都需要简洁参考，理解取消风险时都可能需要解释。借用 Diátaxis 对参考与解释的区分，再增加适用范围、导航与验证——它不意味着每个知识点都要手工写两份"人版"和"AI 版"。

错误的重复，重复的是维护责任：参数参考、排障教程和项目指令都写着"等待 30 秒"，改成 60 秒就要三个维护者记住一起改。有用的自检不是"这句话出现过几次"，而是：改一个易变事实，需要同步修改几个独立维护的当前值？历史复盘仍可写"当时使用 30 秒"，它描述的是明确时点的过去。

链接解决双写，却不自动解决可用性：人可能没点，Agent 可能只读当前片段。对需要即时作决定的路径，入口应说明什么时候必须读取目标。检查的是从任务、入口、搜索、读取、追溯、解释到外部核对的链路——一份资料没进入本次可用上下文，就不能指望它约束本次回答。命中路径不等于取得适用知识：需要保留的可观察材料是搜索词与候选路径、实际读取的片段及版本、随后给出的答案或动作。

使用验证

分开核实事实、资料支持与任务判断，别合成一个"知识库准确率"

三类检查对象分开：事实是否仍成立（对照审核依据）；回答是否得到资料支持（能否从实际取得的资料推出）；任务是否被正确处理（满足当前策略与权限边界）。读旧文回答 30 秒可以在"忠实于所读材料"上表现良好却不符合当前策略；没有任何来源却猜出 60 秒，数值正确也不能证明导航有效。

一次可解释的检查要登记固定条件：被测文档快照、指令、配置、工具范围、问题与初始状态、外部判据；"开新窗口"不是自动隔离全部信息的保证。报告保留失败分布——是事实题错，还是读到事实却在决策题上错？自动化是放大已清楚的判据，不是替模糊标准盖章；不可接受的越权动作与一般措辞变差，不能靠同一个平均及格分决定。

变更维护

来源、使用与模板怎样共同演进

假设 release-3 把等待上限改成 90 秒，不是全库搜索"60"替换成"90"，而是逐个判断对象：当前策略正本依据已审核新规则更新；release-2 历史说明保留 60 秒与版本标识——历史不能随当前配置被重写；排障解释检查推理是否仍成立；生成参考按声明来源重新生成；题库新增 release-3 任务、保留仍支持的 release-2 题、修订已失效预期；文档入口检查"当前版本"是否仍指向正确范围——正本正确却被入口绕过，仍然不可用。

复核动作应该有状态，而不只是一个日期：可记录"已核实仍适用""已更新""因缺权限待核实""该版本已退役"。无法确认生产现值时，更新日期并写"已检查"反而制造信任错觉。多项目复用：共享方法，不共享环境事实——项目 A 的 60 秒和项目 B 的 120 秒不同可能完全正确；模板共享的是"每条高风险事实登记适用范围"这类通用方法，实际配置值由各项目自己填。

案例验证

用一条错误建议检验总体设计：从缺口到修订对象

回到开头的建议：J17 该不该取消。调查链：看实际读取记录——搜索命中 archive/release-1 旧片段，读出的区域缺版本标识；定位缺口——正本没过期，也没证据是模型解释错，缺口是没取得当前策略及适用范围；对照实验——直接提供当前策略后改为"查询 J17，不直接取消或重提"，它的用途是选下一项调查，不是给模型发永久合格证。

核实后的规则是条件分支：客户端最多等待 60 秒，等不到结果返回"仍在处理中"并保留任务号，后台任务不因此被取消；重新提交需要原任务明确失败并确认可重试；取消需要用户明确要求且服务返回可取消。45 秒的运行时长本身不能证明已到等待上限，"运行中优先查询原任务"是默认处理，不禁止在授权且可取消时取消。不同观察对应不同修订对象：文档与依据不符改事实说明与维护责任；只取得旧页改导航与版本标识；给了策略仍解释错改语义与判据；答案被评错改参考答案与评分。

起步

怎样起步，以及什么时候不必搭完整体系

先挑一个近期反复答错、且错误会影响行动的问题，用它检查职责是否已有人承担：审核适用规则 → 找到现有文档正本 → 观察一次真实读取与使用 → 判断缺口 → 修正对应对象 → 回到正常入口复测 → 登记后续变更责任。交付物不是"重构了 20 篇文档"，而是能回答五个具体问题：J17 按哪套策略处理；谁维护它；Agent 实际如何取得它；修订解决了哪个缺口；下次策略变化时哪些对象会被复核。

起步时守住四项职责：事实有人负责，资料能被取得，使用过程可以检查，变化会触发维护。任一项都不能由其余项代替：结构漂亮不代表事实正确，引用正确不代表决策正确，答题通过不代表文档永不过期。目录分层、生成视图、自动回归与模板同步，应随实际使用中的问题逐步增加。

依据与边界

依据、适用边界与待验证之处

本文讨论项目文档如何支持人和编码 Agent 的协作，不提供特定产品的加载规则，也不声称消除模型误读。来源分工：Anthropic 上下文工程文章支撑按需取得资料；Diátaxis 支撑参考与解释的任务区分，不据此推出人和模型必须各维护一份；LangSmith 评测教程支撑把答案正确性、资料支持程度与检索相关性分开检查；Docs as Code 支撑文档进入版本控制与测试工作流。

仍需在实际项目验证三件事：入口与表达改动是否稳定减少目标失败；关键题的维护成本是否可接受；变化触发机制能覆盖多少真实漂移。本文的贡献是把知识归属、取得过程、行为检查和变更维护接成一套可审查的方法，不是另造一种"准确率"或宣布一套普适最优目录。
