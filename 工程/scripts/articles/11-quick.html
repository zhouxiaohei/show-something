01 / 总判断

通用自主 loop 通常由模型决定策略，计划不一定先完整列出

人预设流程、模型动态拆任务、外层流程与内层模型混用，都可以成立。先区分步骤从哪里来，再讨论计划和执行。

需要同时校正：拆任务并非预设工作流专属；执行程序也能检查测试、订单、计算规则等实质条件，能力不止格式校验。内容是否充分，仍依赖模型或人。

先把术语翻译成具体事情

上下文：本次实际递给模型的材料。状态：程序记的已做、待做、等待事项。内容判断：读懂后决定意味着什么、是否切题。候选答复：模型准备交付、由程序接着处理收尾的答复。

判断事项通常谁判断程序实际控制什么
拆哪些任务、顺序是否合理[M] 模型；工作流可由人预设提供指令与模式，保存步骤，按已记录的先后关系调度
结果意味着什么、是否该换路线[M] 模型；明确规则可由代码判断提供观察，触发检查，执行固定分支或新计划
是否切题、论证是否充分[M] 模型 / [H] 人另调评审、给标准与证据、按结果继续或结束
测试失败、预算耗尽、订单存在[C] 程序 检查明确条件读取真实状态并实施规则；不自动覆盖全部需求

02 / 分析四家

从同一个例子看：模型想什么，程序做什么

四家都反复进行“程序提供材料 → 模型决定下一步 → 程序执行并交回结果”。下面把每一步的责任说开，源码函数名留在资料索引里。

统一构造例子两份项目报告互相矛盾，怎样给出说明？

报告 A 说“基本完成”，报告 B 说“还有很多未做”。用户要求：解释差异、列未决问题，并保存说明。示例用于解释机制，不是四家实测结果。

Hermes：模型安排工作，程序替它执行和记进度

程序给模型工具和“复杂工作请记清单”的提示；是否先列计划、列什么，主要还是模型判断。

什么时候程序做什么模型做什么
开始：程序 → 模型把原问题、规则和读取文件等能力交给模型，发起调用。理解任务，决定先读两份报告，或先登记暂定步骤。
中间：模型 → 程序 → 模型执行读取；把内容或错误交回；保存模型提出的清单更新。例如发现日期不同，决定先核对日期，修改查证顺序；不必另有一次专门重规划调用。
收尾：模型提议，程序处理接到准备交付的答复，检查待执行动作及已配置检查，按实际条件继续或返回。判断解释是否充分、未决项是否遗漏；提出交付，或依据检查反馈继续查、继续改。
用例子说明：模型漏掉“列未决项”，程序仍可能忠实保存一张漏项清单。把清单标为“已完成”，并不会自动补出这一要求。

这个版本的特别之处：有一项默认关闭的可选收尾检查，主要看代码修改及验证记录。程序决定是否发出核查提醒，模型决定怎样核查；它不自动判断任意报告是否切题。

AgentScope：程序按当前记录接续，模型决定查什么

原来的函数名，实际是在说：有动作就执行、需要确认就等、结果回来再让模型判断、可以返回时处理结束。

什么时候程序做什么模型做什么
开始：程序 → 模型建立本轮记录、准备输入并发起请求。理解任务，选择先查材料还是回答；不强制所有任务先另调一个规划模型。
中间：动作与判断接力处理读取等动作，记录结果；如需确认或外部结果，就暂停等待，再接着运行。解释报告、提出下一步；如用清单，则给出步骤、先后关系及进度。
收尾：模型提议，程序返回检查是否还有待执行动作、待确认事项或额外检查；处理后决定继续还是返回答复。形成解释与未决项，判断还缺什么；另设内容评审时，由评审模型或人读内容。
用例子说明：程序能记住“报告 A 已读、报告 B 还在等结果”，让任务恢复后接着做。是否读懂了矛盾、是否还缺一条重要证据，仍需要内容判断。

完成标记意味着什么：程序记录“本轮已结束”或“约定字段已生成”，不代表报告已经回答完整。就像表格填满了，也可能没有答到问题。

Codex：模型选择操作，程序交回真实执行结果

模型在实际工作区里读、写和检查；程序把文件内容、改动与检查结果交回来，供模型继续判断。

什么时候程序做什么模型做什么
开始：程序 → 模型提供任务、工作环境信息和可用动作，发起请求。决定先找报告、先读文件还是先记步骤；进度清单的内容也由模型提交。
中间：模型 → 程序 → 模型执行获准的读取、编辑或检查，返回真实内容、差异和错误。发现日期不同时重查口径；写完说明后，决定检查遗漏、修改说明或继续查证。
收尾：模型提议，程序检查检查是否还有待处理动作、新输入或阻止结束的已配置检查；需要时送回反馈继续调用。提出答复；如果程序另发起评审，评审模型读内容，主模型再按反馈修改。
用例子说明：“说明文件已保存”可以是程序检查结果，但“是否遗漏用户要求的未决问题”通常还要模型或人读内容。

别混淆：执行中的进度清单与专门的计划模式不同。程序保存清单，不是在替模型生成正确计划；独立评审也需要明确发起。

Claude Code：模型选择路线，程序可在结束前加检查

模型根据材料决定下一步。程序负责准备材料、执行动作，还可按开发者的配置在收尾时多做一项检查。

什么时候程序做什么模型做什么
开始：程序 → 模型交入任务、规则和可用能力；启用计划模式时，按模式限制当前动作。理解需要、调查材料并写计划；计划内容并不是程序自动算出来的。
中间：程序反馈，模型调整执行动作，把结果及用户新要求送入后续调用。识别矛盾、改查证顺序；用户纠正范围时，理解新要求与旧约束的关系。
收尾：模型提议，程序可加检查在收尾位置运行已配置检查，按结果允许结束或继续。主模型提出答复；若检查再调用模型，评审模型判断遗漏，主模型负责修订。
用例子说明：可以让脚本检查文件是否存在，也可以让程序另请模型对照“解释差异、列未决项”检查内容。发起检查的是程序；第二种检查的结论来自评审模型。

结束时检查（Hook）：就是事先约定“走到这里，多做一项检查”。是否启用、用脚本还是模型，都要看配置。它不是默认就能准确验收所有答案。

“两者一起”要展开：开始由程序发请求、模型读任务；中间由模型选动作、程序执行、模型看结果；收尾由模型提出交付、程序按已配置条件继续或结束。若另加内容评审，仍需说明是哪一个模型在判断。
03 / 再总：实际调用链

模型理解与计划校准，常发生在同一次正常调用中

模型在一次调用里的思考，不一定被写成一张完整任务表。意图理解、规划、执行后分析，是解释谁做什么的词；只有系统明确拆成独立请求时，才是多次 API 调用。

哪些结束信号容易被误读？
信号实际能说明不能证明
请求执行动作（如 tool_use）需要执行动作，把结果放入后续输入计划正确或该动作有价值
本次生成收尾（如 end_turn）程序可以处理继续或结束没有漏任务、答案满足用户
输出被长度限制截断（如 max_tokens）生成被限制，可能不完整正常完成
限流、额度、网络异常API 或资源错误；应走错误路径模型主动完成
轮次或预算耗尽程序必须停止或降级未完成事项已解决
清单全部 completed登记状态均已标完成初始需求完整、工作实际已核实

各家字段不同，需结合响应内容、待处理动作与错误处理；不能只看一个停止枚举。

04 / 分：计划与过程校准

触发可以硬编码，新的解题策略仍可能由模型判断

“模型主动规划”与“指令要求它规划”可以同时成立。模式决定当前允许什么，工具保存模型提交什么；两者都不能独立证明模型理解完整。

并行也是同样的分工：模型或人提出任务实际需要的先后顺序；系统若实现依赖校验与调度，程序可按登记关系推进，普通并发器未必检查依赖。没有登记的任务实际需要的先后顺序也不会自动出现。

05 / 分：候选输出之后

要确保新增一轮模型复核，必须把调用显式安排进去

初始提示写“回答前检查”，可能促使模型自检、运行测试或委托复核；它不证明程序设置了必经的独立复核调用。下图四种路径可组合，但不是所有产品的默认流程。

观察：同一份候选结果，可以进入哪条控制路径？教学演示 · 不运行真实模型
  1. [M] 产生候选答复，可能已自检，也可能遗漏要求。
  2. [C] 无待执行动作，且未配置额外检查，结束本轮。

额外模型调用：没有保证。 结束本轮不等于独立验收通过。

评审必须拿到什么

原始问题当前有效要求候选产物真实检查结果已知缺口

只让评审阅读执行者“已全部完成”的总结，可能继承同一遗漏。只问模型一次的收尾检查 拿到历史文件路径，也不等于读取了历史全文。

失败分支必须存在：检查失败、评审无法判断、响应无效或预算耗尽，要能返回部分完成、受阻或待复核。不能因重试结束就自动升级为成功。

若候选内容已流式展示，后续检查不能撤回用户已经看过的内容。业务若要求通过后才发布，需区分预览和正式交付。

06 / 风险主线

拆解、执行、自评可能共同维护一个错误理解

风险程序能改善什么仍然依赖什么
最初漏掉要求保存原问题、需求与产物对应需求抽取和覆盖判断可能也由模型完成
任务状态假完成要求验证记录、查询真实环境记录是否覆盖任务，状态是否有可信证据
执行偏离但动作都成功保留目标、配置检查点行动是否真正解决原问题
纠正破坏旧约束版本化有效要求与变更自然语言修改关系的理解
压缩丢失 / 旧计划锚定外部状态、原文回读、失效标记摘要正确、知道何时重读与改向
自评或多模型共同误判分开材料与评审路径、组合检查共享盲点不会自动消失
测试通过但业务不符独立场景、最后的实际结果与回归评测验收标准本身是否完整

更多步骤、更多模型、更严格 JSON，都不能单独证明“全部满足”。判断者、标准和证据必须逐项追清。

07 / 人机协作

模型没有承担好的判断，会作为协作成本回到人身上

用户给的协作可靠性文章，把问题放在累计目标稳定性、人工纠偏与失败恢复上。本专题进一步把这些成本对应到 loop 的理解、计划、执行、压缩和验收环节。

相关研究在各自设置下观察到：同一套执行程序 下模型所需纠正量不同，相近解决率可能对应不同过程成本，专业模拟用户的反馈会改变功能测试结果。这些发现支持测量协作条件，不足以证明普遍产品排名。

人承担的工作对应系统薄弱处值得记录的结果
不断把要求写得更明确初始理解与任务漏建表达字数、澄清质量、原需求覆盖
盯住每一步是否跑偏规划与过程校准监督时间、错误暴露时间
反复纠正同一处并重申旧要求纠正吸收与约束保持纠正后是否破坏仍有效约束
重开会话、重建计划和证据上下文与恢复恢复轮次、人工时间、丢失内容
为什么不直接沿用文章的产品排名和数字？

文章对 Claude 的相对偏好是综合判断。统一 OpenCode 比较模型，不能直接证明两个产品优劣；模型与执行程序 同时变化的实验不能分别归因；issue 没有发生率分母。SWE-Journey 的 Final F2P 是功能测试失败转通过指标，不能泛称完整任务成功率。

人工逐项拆分可以接管，但不是唯一方案

还可采用关键阶段人工确认、稳定业务流程加模型子任务、真实反馈加独立评审。选择取决于模型能力与任务可验证性。人逐项指挥会提高人工负担，拆得过碎还可能损失整体语境。

如果系统中的模型和检查都缺少关键知识，继续包装流程无法保证补足能力。需要补充资料、收窄目标，或引入懂这个问题的人。

08 / 场景展开：情报研判

“数据消失”不能从计划开始就变成“异常行动”

构造案例：某区域多架航空器 ADS-B 航迹同时消失，用户希望解释原因。若模型直接开始收集“行动迹象”，计划本身就可能带入未经确认的前提。

程序可检查仍需模型或分析人员判断
引用存在、原文可回查、抓取时间与窗口来源是否可信、原文是否真正支持论断
已知上游 ID、重复链接、字段一致性不同材料是否实质同源、证据是否独立
规定问题是否都有对应材料竞争解释是否漏项、反证是否有区分力
状态与必填项一致、已知缺口被登记结论是否超出证据、不确定性表达是否合适
调查可以在规定范围内完成交付，同时保留“证据无法区分两种解释”。报告写完、调查结束与真相已确定，必须分开。

09 / 提示词、状态与长内容

模型每一轮只依据实际进入输入的内容判断

提示词可以修正

模板里的错字和过期规则可以更改、删除并版本化。对话中的历史错误通常以更正和当前有效状态处理；不能把矛盾规则不断追加就算解决。

状态保存也会出错

任务板、摘要和验证记录都可能由模型填写。要保留它们的依据与未决项，避免下一轮只继承一句“已经核实”。

10 / 用 grill 看懂技能怎样工作

每轮新问题由模型生成，一轮可以问多题

用户回答以后，要针对回答生成下一轮问题，需要模型再次处理对话。不是每道题固定一次请求；读资料、调用工具或研究任务还可能增加调用。等待用户时，这份技能本身不要求持续运行模型。

层次实际做什么本例问答技能的情况
技能规则规定怎样组织问答、等待和收尾入口要求采用提问规则：找关键选择、一次问当前可答的问题、等回答再调整。
模型判断理解回答，决定具体问什么、哪些还没解决没有独立脚本能替模型理解所有答案；是否问完仍可能误判。
执行程序加载或提供规则，保存对话，组织模型和工具调用显示问题、接收回答，把新信息送入后续处理；技能不是另一个后台模型引擎。
构造例子

用户说“比较两种情报解释，每日更新”。程序把这段话送回；模型才会决定下一轮问“证据来自哪里”“多久失效”。如果模型没想到来源独立性很关键，技能也不会自动替它补问。

技能还要求：模型认为问题问完后，开始后续实施前先取得用户确认。这是模型需遵循的文字规则，不是自带代码审批门。当前用户明确要求科普、不要访谈时，不应机械追问。

11 / 演进、成本与取舍

提高可验证性，也持续检验模型与执行程序 的能力边界

01

模型更能保持目标

规划、解释反馈和长程执行进步后，重新评测哪些外部补偿仍有用，移除造成僵化的旧结构。

02

更多结果可外部核验

用环境状态、独立测试和明确条件减少单靠自报；复杂内容应该怎样验收仍是难点。

03

评审看到有效证据

提供原需求与结果，校准评审错误；分离生成与评价会增加机会，也会增加费用与误判路径。

04

失败进入评测与改进

把漏项、假完成和纠正失效变成可重放案例，验证修改是否有效，而非持续追加提醒。

这是对公开研究的归纳，不是统一行业路线图。复核、多 Agent 和长上下文都有费用与延迟；增加多少值得，必须按任务测。
