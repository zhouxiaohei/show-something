# Claude Code 与 Codex 真实协作可靠性调研

> 研究快照：截至 2026-07-17  
> 目标读者：实际使用过编码代理、关心生产协作质量的技术负责人和资深开发者  
> 研究对象：Claude/Claude Code 与 GPT/Codex，但严格区分模型、代理框架和产品界面  
> 核心问题：面对模糊、口语化、依赖上下文并持续变化的真实需求，哪个系统更容易建立正确目标、减少人工纠偏，并在失败后继续迭代？

## 一、执行摘要

### 1. 核心立场

评价编码代理，不能只看它在一份目标明确、验收条件完整的任务说明下，最终是否通过测试。真实软件协作更常见的起点是：用户只说出一个不完整、口语化、依赖项目背景的意图，随后在多轮交流中补充约束、否定局部方案、改变优先级，并要求代理在已有结果上继续迭代。

在这种场景里，最关键的能力不是一次性“解题能力”，而是能否建立并持续维护一个正确的**任务模型**：代理当前认为用户究竟要什么、哪些约束仍然有效、哪些要求被后续消息局部修改、完成标准是什么，以及当前证据是否足以支持继续执行。

本报告的综合判断是：

> **现有公开证据初步支持 Claude/Claude Code 在模糊意图理解、多轮目标保持、较低用户纠偏成本和失败后的持续协作方面优于 GPT/Codex。Codex 并不缺少执行与解题能力，但更容易在长任务、连续纠正、上下文压缩和自动续跑中损坏内部任务模型；一旦损坏，其较强的执行倾向会加速混乱。** `[综合推断]`

这不是“Claude 不会犯错、Codex 一定犯错”。两者都是概率模型，都会产生幻觉、遗漏和错误操作。差别更可能体现在：

- 错误发生的概率；
- 错误是否容易被用户发现；
- 用户需要投入多少认知劳动才能纠正；
- 纠正能否被完整吸收，而不是覆盖另一条旧约束；
- 长会话后是否仍能在已有成果上继续迭代；
- 失败时是否暴露了足够清晰的中间认知模型。

### 2. 当前证据最明确支持什么

1. **真实多轮协作需要独立评价。** SWE-Together 从 11,260 条真实用户—代理会话中重建了 109 个可复现的多轮任务，并直接统计用户纠正次数。它证明“最终正确率相近”不能代表协作体验相近。`[模型证据｜预印本]`
2. **较强模型通常需要更少人工纠正。** SWE-Together 中，Claude Opus 4.8 同时取得最高最终质量、最高稳定重复成功率和最低用户纠正量；GPT-5.5 次之。能力与用户纠正量呈强负相关。`[模型证据｜预印本]`
3. **Codex 的最终成功率可以很高，但过程可能更不稳定。** TraceProbe 对 2,500 条轨迹的分析中，Codex + GPT-5.4 的解决率略高于 Claude Code + Opus 4.6，但失败动作、有害动作比例更高，工具成功率更低。`[框架与模型混合证据｜预印本]`
4. **Codex 长会话丢失累计约束是已公开报告的真实失败模式。** openai/codex issue #33262 描述了上下文压缩后只能复述大致任务，却遗漏强制规则、重新引入已排除工作，并在用户多次重述后继续按不完整摘要行动。`[产品案例｜无分母]`
5. **Claude Code 也存在压缩、恢复和指令丢失问题。** 因此差异不是“有或没有”，而是概率、严重程度、失败形态以及恢复成本。`[产品案例｜无分母]`

### 3. 当前证据不能证明什么

- 不能根据 GitHub issue 数量计算两者真实失败率；公开 issue 没有总使用次数这个分母。
- 不能把 Claude 模型在统一 OpenCode 框架中的优势，直接等同为 Claude Code 产品优势。
- 不能把 Codex 在 Terminal-Bench 或明确 GitHub issue 修复上的高分，外推为它更擅长模糊需求和长期协作。
- 不能用少数用户体验证明所有项目、模型版本和权限配置下都如此。
- 当前尚无成熟权威评测同时覆盖：真实口语输入、隐性业务背景、长会话压缩、用户纠正吸收、失败解释质量和多轮持续迭代。

## 二、真正应该比较的不是“简单与复杂”，而是协作不确定性

传统评测常把任务分成简单和复杂，但这个分类信息量有限。一个跨几十个文件的机械迁移可能很长，却几乎没有业务判断；一个只改五行的需求可能依赖隐含产品语义、历史否决方案和接口契约，反而更难。

真实协作难度至少由以下变量共同决定：

| 变量 | 真实影响 |
|---|---|
| 初始表达完整度 | 用户是否已经把意图写成规格书 |
| 上下文依赖 | 是否必须结合代码、历史对话和业务背景理解 |
| 需求歧义 | 是否存在多个表面合理、实际不同的解释 |
| 约束累积 | 后续消息是替换旧目标，还是只修改其中一部分 |
| 反馈可观察性 | 错误是否能通过测试、日志或 UI 直接发现 |
| 路径长度 | 从理解到交付需要多少连续正确判断 |
| 人类干预 | 用户是否必须持续检查、解释和纠偏 |
| 恢复难度 | 跑偏后能否低成本恢复共同理解 |
| 上下文压缩 | 长会话后哪些细节、决策和边界会丢失 |
| 失败透明度 | 用户是否知道代理为什么失败、下一步改什么 |

因此，本报告采用三条主线评价真实协作可靠性：

1. 任务模型的建立与持续稳定性；
2. 总人类协作成本；
3. 失败的可解释性与可恢复性。

## 三、第一主线：任务模型的建立与持续稳定性

### 1. 什么是任务模型

任务模型不是代理输出的一份漂亮计划，而是它在执行时实际依赖的内部工作表示，至少应包含：

- 用户真正想获得的结果；
- 当前代码和环境的事实；
- 已确认与未确认的假设；
- 必须保留的约束；
- 明确排除的范围；
- 后续消息修改了旧目标的哪一部分；
- 当前完成状态和验证标准。

真实协作链条可以表示为：

```text
理解模糊、口语化表达
→ 结合代码和历史对话恢复真实意图
→ 把新纠正合并进累计目标
→ 长会话和压缩后保持完整约束
→ 依据同一个目标持续执行和验证
→ 在已有结果上继续迭代
```

其中任何一环损坏，后续步骤都可能高度自洽却整体错误。

### 2. Claude 的优势更可能是“语义主线稳定”

持续使用观察表明，Claude Code 面对口语化需求时，通常更容易形成一个可协商的整体理解：它会把用户的表达、现有代码、前几轮否定和当前目标组织成一条相对稳定的语义主线。即使第一次没有完全做对，用户往往仍能基于它呈现的理解继续修订。`[用户观察]`

SWE-Together 为这一观察提供了目前最接近的外部证据。该评测没有在第一轮提供完整规格，而是从真实多轮会话重建任务，让模拟用户根据代理轨迹逐步释放澄清、纠正和新增要求。结果中 Claude Opus 4.8 的最终完成质量和稳定重复成功率最高，同时需要的纠正最少。`[模型证据｜预印本]`

这不能直接证明 Claude Code 的产品机制更强，因为实验统一使用 OpenCode 框架；但它较强地支持：Claude 模型更容易从渐进、多轮、不完整的用户意图中形成较可靠结果。`[证据边界]`

### 3. Codex 的典型风险是累计目标碎裂

Codex 的问题通常不是完全听不懂第一句话，而是随着任务推进，内部任务表示逐渐退化：

```text
最初目标
→ 增加约束 A
→ 否定局部方案 B
→ 补充边界 C
→ 工具输出和子代理结果进入上下文
→ 自动压缩或任务交接
→ 只剩下不完整的目标摘要
```

此后它可能仍能复述“大概要做什么”，但执行时已经遗漏某些关键约束。用户再次纠正后，它又可能把最新一句当成当前全部目标，而不是对累计任务模型做局部更新。`[用户观察｜综合推断]`

openai/codex issue #33262 是这一现象的直接案例：报告者在长仓库任务中不断增加明确约束，并声明后续消息只修改指定部分，其余规则继续有效；上下文压缩后，Codex 可以近似描述任务，却遗漏“先文档后代码”等强制规则、重新引入明确排除的工作，把完整交付任务缩减成几个通用步骤。用户多次重述完整契约后，后续执行仍像只保留了最新消息或不完整摘要。`[产品案例｜无分母]`

相关公开症状还包括：

- 重复读取上下文中已经存在且没有变化的文件；
- task handoff 后提前停止，而不是继续执行；
- 请求为 token rollover 增加原子化任务交接；
- 长会话需要主动排除无关上下文；
- IDE 在数小时后重新投递旧用户消息并执行过期修改；
- Goal 声称会恢复计划，但没有真正继续。

这些 issue 只能证明失败模式存在，不能证明发生率高于 Claude Code。`[证据边界]`

### 4. 为什么长会话后会“一团浆糊”

当任务模型损坏时，Codex 仍可能继续表现出很强的局部执行能力：搜索文件、运行命令、修改代码、更新计划。问题在于，这些动作不再由同一个完整目标约束。

于是用户会看到：

- 每一步单独看都像有理由；
- 当前回答似乎仍围绕主题；
- 但不同步骤隐含的目标已经不一致；
- 新修改修复了一个问题，却重新引入旧问题；
- 计划、实现、验证和总结互相对不上；
- 用户无法判断应该纠正哪一层。

这不是单纯的“记忆容量不足”，而是缺少稳定、可检查、可增量更新的累计任务契约。`[综合推断]`

## 四、第二主线：总人类协作成本

### 1. 不能只统计用户发了几条消息

人类协作成本至少包含四部分：

| 成本 | 含义 |
|---|---|
| 需求显式化成本 | 用户需要把自然表达改写得多像机器规格书 |
| 过程监督成本 | 是否必须频繁检查代理有没有跑偏 |
| 纠偏成本 | 指出错误后需要多少轮才能真正吸收 |
| 恢复成本 | 会话混乱后能否修复，还是只能新开任务重来 |

两个代理最终都提交了通过测试的代码，并不代表它们给用户创造了相同价值。如果其中一个需要用户持续盯住、反复重述背景并检查每次修改，最终成功率会掩盖大量人类劳动。

### 2. SWE-Together 首次把“用户纠正”放进主要指标

SWE-Together 定义了 User Correction：

```text
用户纠正分 = 明确纠正次数 + 0.2 × 软性提醒次数
```

明确纠正指用户直接指出错误、不完整或跑偏；软性提醒包括“再检查一下”“你确定吗”等较轻的纠偏压力。

109 个任务、每个模型两次独立运行的主要结果如下：

| 模型（统一 OpenCode 框架） | pass@1 | 两次均成功 pass² | 平均质量 | 用户纠正，越低越好 |
|---|---:|---:|---:|---:|
| Claude Opus 4.8 | 63% | 52% | 0.801 | 1.38 |
| GPT-5.5 | 58% | 48% | 0.763 | 1.59 |
| Claude Opus 4.6 | 58% | 46% | 0.755 | 1.59 |
| GLM-5.2 | 55% | 42% | 0.735 | 1.53 |
| DeepSeek V4 Pro | 48% | 29% | 0.679 | 1.76 |
| MiniMax 2.7 | 40% | 26% | 0.630 | 2.17 |

Claude Opus 4.8 不只是最后分数最高，也需要最少纠正。论文报告能力与用户纠正量高度负相关：pass@1 与纠正量的 Pearson 相关系数为 -0.92，稳定解决率与纠正量为 -0.84。`[模型证据｜预印本]`

需要谨慎解释两点：

1. Claude Opus 4.8 与 GPT-5.5 的平均纠正差距是 0.21，并非数量级差距；真正重要的是 Claude 在更少纠正的同时取得更高质量和更高稳定成功率。
2. Claude Opus 4.6 与 GPT-5.5 的纠正量相同，说明“Claude 系列必然更少纠正”并不成立，版本和能力水平仍然重要。

### 3. 用户体验差距可能被累计成本放大

即使单轮平均只多 0.21 次纠正，实际生产体验也可能出现更大差距，因为纠正不是等价的。

一次低成本纠正可能是：

> 后端逻辑保留，只是不在前端暴露。

代理理解后即可继续。

一次高成本纠正可能要求用户先完成：

1. 判断代理究竟误解了哪一层；
2. 重新说明最初业务目的；
3. 重述仍然有效的旧约束；
4. 指出哪些代码可以保留；
5. 阻止它继续扩大错误修改；
6. 再检查新纠正是否损坏另一条要求。

因此，真正需要测量的不是消息条数，而是**纠正所需认知劳动**。当前公开 benchmark 仍缺少这一指标。`[测评缺口]`

### 4. 为什么 Claude 的错误可能更容易继续迭代

持续使用观察中，Claude Code 并非总是一次完成，但经常能交付一个结构基本正确、可继续修改的中间结果。用户可以说“这一部分不对，按刚才第二个目标改”，后续仍能继承已有成果。`[用户观察]`

Codex 更常出现另一种情况：前几轮每次都完成了局部动作，但累计状态已经无法清晰解释；继续纠正时，新信息与旧摘要相互覆盖，用户投入越来越多，最终新开会话反而更便宜。`[用户观察]`

这说明持续迭代能力不是单次成功率，而是：

```text
当前结果质量
× 目标保持概率
× 纠正吸收率
× 状态可解释性
× 下一轮可继承性
```

## 五、第三主线：失败的可解释性与可恢复性

### 1. 可解释性不是“总结写得好看”

代理失败时，真正有用的解释应回答：

- 它当前如何理解目标；
- 哪些是代码事实，哪些是假设；
- 从哪一步开始与预期不一致；
- 哪些约束仍然有效；
- 哪些部分已经完成并验证；
- 哪些部分没有完成；
- 为什么无法完成；
- 用户最少需要补充什么才能继续。

一个语言流畅、结构完整的最终总结，如果没有暴露错误的任务理解，仍然不可用于纠偏。

### 2. Claude 常提供“可编辑的中间认知模型”

Claude Code 的主观优势之一，是它更经常把自己的理解、证据和不确定性组织成用户可修改的叙事。用户不一定相信该叙事完全正确，但可以指出其中哪条假设不成立，然后继续推进。`[用户观察]`

这类能力很难由现有代码测试捕获。SWE-Together 的 User Correction 只能统计纠正量，不能测量每次纠正需要多少解释；TraceProbe 可以识别搜索循环、验证遗漏和不受支持的完成声明，但还不能判断失败解释是否让用户真正理解了问题。`[测评缺口]`

### 3. Codex 更常暴露动作，而不是暴露任务理解

Codex 失败时经常可以列出：看了什么文件、改了什么、哪个命令失败、哪些测试没跑。但用户仍然不知道：

- 它为什么选择这个方向；
- 它现在认为最终目标是什么；
- 它是否还记得早期限制；
- 它把哪个推断误当成事实；
- 下一条提示应该修正需求、方案还是验证方式。

于是用户必须从动作轨迹反推它内部已经损坏的任务模型。这会让纠偏成本非线性增长。`[用户观察｜综合推断]`

### 4. “显式失败”通常比“隐式目标损坏”更容易处理

Claude Code 和 Codex 都可能卡住、压缩失败、工具不可用或明确报告无法继续。这些显式故障虽然令人烦恼，但用户知道需要重试、授权、补充信息或切换方案。

更危险的情况是：代理仍然持续输出相关内容、调用工具并汇报进度，但执行所依据的累计目标已经不完整。此时系统没有报错，用户却在为错误方向持续支付时间和 token。

Codex GitHub 中“可以近似复述任务但执行时遗漏累计约束”的案例，说明这种隐式损坏真实存在。`[产品案例｜无分母]`

## 六、模型、代理框架与产品界面必须分层

### 1. 模型层

模型层关注：

- 自然语言与隐含意图理解；
- 多轮语义一致性；
- 对纠正的吸收；
- 不确定性表达；
- 推理与代码生成能力。

SWE-Together 统一使用 OpenCode，因此其 Claude Opus 4.8 对 GPT-5.5 的优势主要属于模型层证据。`[模型证据]`

### 2. 代理框架层

框架层关注：

- 给模型提供了哪些工具与状态；
- 如何保存计划和任务进度；
- 如何进行上下文压缩；
- 如何恢复任务；
- 子代理如何继承上下文；
- 工具失败后怎样重试和回滚；
- 完成判断怎样触发。

TraceProbe 比较 Claude Code + Opus 4.6 与 Codex + GPT-5.4，模型和框架同时变化，因而属于混合证据。研究还用 OpenCode 分别运行相同模型，尝试分离 scaffold 效应，但无法完成 Claude Code × GPT 与 Codex × Claude 的完整交叉实验。`[证据边界]`

### 3. 产品界面层

产品层关注：

- CLI、IDE、桌面端如何展示状态；
- 用户能否看到上下文使用量；
- Plan、Goal、自动续跑如何切换；
- 权限和 sandbox 是否打断工作；
- 会话恢复、消息队列和后台任务是否可靠；
- 用户能否暂停、修订或回退。

Codex Goal 可以持久化目标并自动续跑，但 Goal 是调度机制，不会自动提高模型的意图理解，也不会保证压缩后的目标仍完整。自动续跑甚至可能放大已经错误的方向。`[官方功能事实｜综合推断]`

## 七、现有权威研究分别测到了什么

### 1. SWE-Together：最接近真实多轮协作

**测量内容：**真实会话重建、渐进意图、模拟用户纠正、最终行为完整度、用户纠正量、两次重复运行稳定性。

**重要价值：**首次把“用户需要纠正多少”作为主要指标，而不是把用户介入当成干扰。

**主要限制：**只有 109 个高精度可复现任务；大量依赖私有背景、线上系统或主观产品判断的真实会话被排除；使用统一 OpenCode，不能直接比较 Claude Code 与 Codex 产品。

### 2. TraceProbe：测执行过程而不是只看最终结果

**测量内容：**搜索循环、重复读取、工具失败、修改回滚、范围漂移、验证遗漏、不受支持的完成声明和轨迹分歧。

主要数据：

| 指标 | Claude Code + Opus 4.6 | Codex + GPT-5.4 |
|---|---:|---:|
| 解决率 | 77.4% | 78.4% |
| 每任务中位步骤 | 27 | 24 |
| 工具调用 | 25 | 41 |
| 工具成功率 | 96.7% | 91.9% |
| 保留动作 | 27.6% | 36.2% |
| 失败动作 | 3.3% | 8.0% |
| 有依据动作 | 36.9% | 32.0% |
| 范围外探索 | 17.6% | 14.3% |
| 有害动作比例 | 0.07 | 0.10 |

**重要价值：**说明 Codex 可以用更多工具、更多失败动作和更高有害动作比例，得到与 Claude Code 接近甚至略高的最终解决率；最终成功不等于过程稳定。

**主要限制：**任务仍来自 SWE-bench；Claude 与 GPT 模型不同；不直接测用户纠正的认知成本和失败解释质量。

### 3. METR Time Horizon：测任务长度与成功概率

METR 用人类专家完成时间标定任务难度，并拟合代理成功概率随任务长度下降的曲线；每个任务进行六次独立运行，还人工检查 reward hacking。

**重要价值：**把“复杂任务”改写成不同可靠性水平下的时间跨度，例如 50% 和 80% time horizon，并明确区分始终成功、始终失败与同任务随机波动。

**主要限制：**任务大多自包含、目标明确并可自动评价；METR 会针对不同模型选择 Claude Code、Codex 或其他 scaffold，不是固定产品正面对比；对模糊业务目标覆盖不足。

### 4. CodeClash：从一次性任务转向长期目标

CodeClash 让模型在多轮竞争中持续改进同一代码库，评价最终系统质量，而不是只提交一次补丁。

**重要价值：**开始测量目标导向、持续改善和多轮策略。

**主要限制：**仍是新基准；不直接测自然用户纠正、失败解释和真实团队上下文。

## 八、GitHub 证据应该怎样使用

### 1. GitHub issue 能证明什么

GitHub issue 可以证明：

- 某类失败确实发生过；
- 失败发生在哪个产品层；
- 是否有复现步骤、日志和版本信息；
- 多个用户是否独立描述了相似症状；
- 官方是否承认、修复或关闭。

### 2. GitHub issue 不能证明什么

它不能直接证明：

- 真实发生概率；
- 哪个产品整体更稳定；
- 每个 issue 是否来自独立底层原因；
- 一个高热度项目是否因为用户更多而 issue 更多；
- 自动关闭和仓库治理差异带来的统计偏差。

所以本报告将 GitHub 用作“失败模式证据”，不用作“失败率排行榜”。

### 3. Codex 相关失败模式聚类

| 失败模式 | 代表案例 | 能支持的结论 |
|---|---|---|
| 累计约束丢失 | openai/codex #33262 | 长会话压缩后可能保留不完整任务契约 |
| 重复读取 | #33498 | 上下文利用可能退化为重复搜索 |
| 交接后提前停止 | #33398 | task handoff 未必可靠恢复执行状态 |
| 需要原子化 rollover | #33310 | 社区认为长任务交接缺少稳定契约 |
| 长会话上下文失控 | #33769 | 用户需要主动控制进入上下文的内容 |
| 过期消息重新执行 | #33819 | 会话队列错误可能导致旧意图重新生效 |
| Goal 恢复不执行 | #33829 | 声称继续与实际继续可能不一致 |

### 4. Claude Code 也存在同类问题

Claude Code GitHub 同样可以找到：

- `/compact` 崩溃或重复执行；
- resume-from-summary 保护未触发；
- context thrashing；
- 中途切换模型后压缩窗口错误；
- 项目设置或 hooks 没有加载；
- 模型忽略用户指令；
- 后台会话和权限状态恢复异常。

因此报告立场不是“Claude Code 稳定、Codex 不稳定”，而是：

> 两者都会失败，但当前研究和持续使用观察更支持 Claude 的协作错误分布较温和、纠偏成本较低；Codex 更容易出现隐式任务模型损坏，并继续执行。`[综合推断]`

## 九、目前最大的测评缺口

真正贴近生产的成对评测至少还应测：

1. **口语理解成本**：用户需要补充多少信息，代理才能准确复述目标。
2. **主动澄清质量**：面对歧义时，是问关键问题、做安全假设，还是直接选择一个方向。
3. **累计约束召回**：十轮后还能否准确列出仍有效、已修改和已取消的要求。
4. **纠正吸收率**：一次纠正后是否解决问题，同时保持无关旧约束。
5. **纠正半衰期**：纠正经过多少轮或一次压缩后开始失效。
6. **假完成率**：宣称完成但行为验收失败的概率。
7. **失败解释可用性**：用户能否仅根据解释判断下一步应修正什么。
8. **恢复成本**：跑偏后需要多少用户 token、多少分钟和多少轮才能恢复。
9. **持续迭代成功率**：在已有修改上连续增加三轮需求后仍保持全部行为的概率。
10. **人工审查时间**：最终结果需要多少时间检查和修复，而不仅是代理运行时间。

## 十、建议的内部成对实验

若要验证个人体验是否具有统计稳定性，应使用同一真实项目、相同初始状态和成对任务进行重复测试。

### 1. 任务类型

- 模糊产品要求：只给自然口语，不提前整理规格；
- 上下文恢复：要求结合项目文档和既有代码推断；
- 局部纠正：后续消息只修改旧目标的一部分；
- 冲突约束：加入看似冲突但可通过澄清解决的要求；
- 长会话：跨越至少一次自动压缩或任务交接；
- 持续迭代：在同一成果上连续追加三轮功能；
- 失败任务：故意提供缺失依赖或无法满足的目标，观察解释质量。

### 2. 实验控制

- Claude Code 与 Codex 使用各自推荐的前沿模型；
- 固定仓库 commit、权限、可用工具和时间预算；
- 每个任务独立运行至少 10 次；
- 不把一方生成的澄清答案直接复制给另一方；
- 保存完整轨迹、diff、命令和用户纠正；
- 最终结果由不知道工具身份的评审者盲评。

### 3. 主要指标

| 指标 | 定义 |
|---|---|
| 首轮目标复述准确率 | 第一次行动前是否正确识别目标、边界和歧义 |
| 主动澄清有效率 | 所提问题是否减少了关键不确定性 |
| 用户纠正次数 | 明确纠正和软性提醒的加权数量 |
| 用户纠正字数 | 用户为恢复目标额外输入的文本量 |
| 约束保持率 | 最终结果保留多少仍有效约束 |
| 纠正吸收率 | 修复指定问题且未破坏其他约束的比例 |
| 假完成率 | 声称完成但盲评或行为验证失败的比例 |
| 严重跑偏率 | 越界修改、错误接口、破坏已有行为等比例 |
| 可恢复率 | 跑偏后两轮内恢复正确方向的比例 |
| 持续迭代率 | 连续三轮新增要求后仍满足全部要求的比例 |
| 人工审查分钟 | 从代理停止到人类确认可接受的时间 |

### 4. 最重要的结果表达

不要只报告平均分，应同时报告：

- 中位数；
- 90 分位监督成本；
- 最坏 10% 的严重失败；
- 同任务多次运行方差；
- “一次成功”和“连续两次都成功”；
- 失败类型分布；
- 用户能够恢复与必须重开会话的比例。

## 十一、综合结论

### 1. 已有证据支持的结论

1. 明确、静态任务 benchmark 不能代表真实编码协作。`[强证据]`
2. 多轮真实会话中，用户纠正量是独立且重要的能力指标。`[强证据]`
3. 最新 SWE-Together 结果中，Claude Opus 4.8 相比 GPT-5.5 取得更高质量、更高稳定成功率和更少用户纠正。`[中强证据｜预印本]`
4. TraceProbe 中 Codex 最终解决率略高，但失败动作和有害动作比例高于 Claude Code。`[中等证据｜模型与框架混合]`
5. Codex 长会话丢失累计约束、重复读取和交接失败是真实存在的产品失败模式。`[案例证据]`
6. Claude Code 也存在上下文压缩、恢复和指令失效问题。`[案例证据]`

### 2. 立场明确但仍需继续验证的判断

> Claude/Claude Code 当前更适合作为需要持续协商的开发合作者；Codex 更像执行能力很强、但内部任务模型稳定性不足的执行器。`[综合推断]`

Claude 的主要优势不一定是每一个固定任务上都能写出更好的代码，而是：

- 更容易从口语和上下文恢复用户意图；
- 更容易维持跨轮次的语义主线；
- 错误后通常需要较少纠正；
- 更常提供可供用户修改的中间理解；
- 更容易交付一个“差不多正确、可以继续迭代”的结果。

Codex 的主要风险也不是简单的编码能力不足，而是：

- 依赖用户把目标提前显式化；
- 容易把最新纠正当成全部目标，而不是增量更新；
- 长任务和压缩后累计约束可能碎裂；
- 失败时动作很多，但内部理解不够透明；
- 一旦跑偏，继续执行可能让已有状态越来越难恢复。

### 3. 最终判断

如果把编码代理理解为“从完整规格到代码的执行工具”，Codex 与 Claude Code 的差距可能有限，且 Codex 在部分终端和明确任务中很强。

如果把编码代理理解为“与人共同发现目标、吸收纠正并持续演化软件的协作者”，现有证据与持续使用观察都更支持 Claude/Claude Code。真正决定体验的不是峰值能力，而是：

```text
自然意图理解
× 任务模型稳定性
× 低人工纠偏成本
× 失败透明度
× 恢复和持续迭代能力
```

这也是未来编码代理测评应当从“任务通过率”转向“协作可靠性”的原因。

## 十三、证据标签说明

| 标签 | 含义 |
|---|---|
| `[模型证据]` | 使用统一框架比较不同模型，主要支持模型层判断 |
| `[框架证据]` | 模型相同或经过控制，主要支持 agent scaffold 判断 |
| `[产品案例]` | 具体产品 issue、日志或复现，只证明失败模式存在 |
| `[用户观察]` | 持续使用形成的经验，用于定义研究问题，不当统计事实 |
| `[综合推断]` | 多类证据共同支持，但尚无直接完整实验验证 |
| `[证据边界]` | 明确说明该证据不能外推到什么结论 |
| `[测评缺口]` | 当前公开研究尚未充分覆盖的维度 |
