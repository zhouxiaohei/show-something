# 为什么 Agent 接入的能力越多，反而越容易变笨

> **文档类型**：机制拆解型文章。回答一个问题：为什么工具接得越多，Agent 反而越容易选错、漏选、绕远路，以及能力应该按什么规则接、按什么规则收。结构模板 A（结论先行）：先给机制与判断，再给设计形态，最后给治理清单。
>
> **断言标注**：`[官方文档]` 厂商一手文档与协议规范；`[经验]` 作者在能力目录审计中的实践观察，未受控；`[推测]` 本文提出的机制假设，附证伪方式。无标注的为可直接核对的定义或事实。全文以 `[经验]` 与 `[推测]` 为主；引用外部材料只标到「有什么」，不替它背书「效果有多好」。
>
> **与第 06 篇的分工**：[第 06 篇](为什么和%20AI%20越聊越乱.md) 讲**对话侧**：上下文里出现两个互相矛盾的版本时会发生什么。本文讲**能力侧**：还没开始对话，光是「能用的东西太多」就已经在收税。两篇共用「上下文是有限预算」这个底层，入口不同。

给 Agent 接入更多工具，看起来应该只会增加能力。

它原本只能读文件，后来能查数据库、浏览网页、发消息、操作云服务、生成报表。每增加一个 Tool，动作空间都变大；接入 MCP 后，一台 Server 又能一次暴露几十个能力。

但实际使用中经常出现相反结果：工具越多，Agent 越容易选错、漏选、重复调用或凭空构造参数。明明系统“拥有”正确工具，模型却绕远路，甚至选择一个名字相近但语义不同的能力。

原因是 Agent 能力并不等于工具总数。模型每次行动前，都要在当前可见的名字、描述、参数 schema 和流程说明中完成一次路由。候选越多、边界越相似、描述越含糊，这次路由越难。

> Agent 的能力上限由它接入了什么决定，实际能力则由它能否在正确时刻找到并正确使用那项能力决定。

## 一、每接入一个 Tool，都要缴三种税

### 1. 上下文税

模型需要知道工具名称、用途、参数和返回含义。若所有 schema 常驻上下文，几十个工具会持续占用窗口，即使当前任务只需要其中两个。`[推测]`

占用窗口不是唯一问题。工具说明会和需求、代码、测试结果争夺注意力。窗口尚未溢出，信噪比已经下降。

### 2. 路由税

模型需要回答：

```text
现在是否应该调用工具？
应该调用哪一个？
调用顺序是什么？
参数从哪里来？
失败后换工具、重试还是停止？
```

当系统里同时存在 `search`、`web_search`、`deep_search`、`topic_search` 和多个 MCP Server 的搜索工具时，工具数量并没有带来五种独立能力，带来的是更多容易混淆的决策分叉。`[经验]` 这条来自能力目录审计中反复出现的重名与近义工具。

### 3. 治理税

每个能力都需要：

- 权限边界；
- 输入输出契约；
- 失败语义；
- 版本兼容；
- 可观测性；
- 测试和评测；
- 维护者。

如果只统计“已经接入多少 Tool”，不统计谁负责、谁能调用、失败怎样处理，能力目录会迅速变成另一种依赖地狱。

## 二、API、CLI、Tool、MCP、Skill 根本不是五选一

很多能力架构问题从概念混乱开始：团队把 API、CLI、Tool、MCP 和 Skill 当成五种竞品，讨论“到底应该用哪一个”。

它们位于不同抽象层，最简单的区分方法是看消费者是谁。

| 概念 | 本质 | 主要消费者 |
|---|---|---|
| API | 程序之间的稳定调用契约 | 代码 |
| CLI | 为终端交互包装的入口 | 人或脚本 |
| Tool | 提供给模型自主选择的原子动作 | LLM |
| MCP | 发现和调用外部工具、资源的标准协议 | Agent 客户端与能力服务端 |
| Skill | 一类任务的流程、知识、脚本和资源包 | LLM |

`[官方文档]` MCP 的定位以官方规范为准；Skill 的分层加载方式见 Anthropic 的 Agent Skills 系列文档。

同一份业务能力可以同时拥有这些形态：

```text
订单服务提供 API
        ↓
CLI 为运维人员提供命令
        ↓
Tool 把“查询订单”暴露给模型
        ↓
MCP Server 标准化暴露一组订单 Tools
        ↓
Skill 教 Agent 怎样查询、核对并生成对账报告
```

因此，MCP 不会替你设计好 Tool，Skill 也不是另一种 API。协议解决连接问题，不能自动解决职责、颗粒度和权限问题。

## 三、真正危险的不是工具多，而是能力同时常驻

假设一个 Agent 理论上拥有 200 项能力，但每次任务只加载最相关的 5 项，它未必存在严重过载。

相反，即使只有 30 个工具，如果它们：

- 全部常驻上下文；
- 名称相似；
- 描述没有写“何时使用”；
- 参数 schema 大而复杂；
- 失败语义不同；
- 多个工具做近似相同的事；

模型也可能持续选错。

所以真正需要治理的是：

> 当前决策点上，同时暴露给模型的候选数量和相似度。

这也是为什么“主上下文里同时可见的能力越少越好”比“系统总能力越少越好”更准确。`[推测]` 这是本文的核心假设：可治理的量是「当前决策点的候选数与相似度」，目录总量只是背景。证伪方式：保持候选数不变、只把目录总量扩大十倍，如果误选率同步上升，这条假设就不成立。

## 四、Skill 的价值不是多一层包装，而是渐进式披露

好的 Skill 通常分三层：

```text
第一层：名称和描述
用于判断是否相关，长期可见。

第二层：主体说明
确认相关后加载流程和关键规则。

第三层：脚本、模板、参考资料
执行到具体步骤时再读取。
```

这是一种上下文预算设计。模型不需要在启动时读完所有领域知识，只需要先知道“有哪些能力、什么时候该用”。`[官方文档]` 渐进式披露的分层加载来自 Anthropic 的 Agent Skills 文档，本文把它重新表述为预算问题。

其中最容易被低估的是 description。它承担的是路由契约的角色，写法上却常被当成宣传语。它至少应该回答：

- 做什么；
- 什么时候使用；
- 什么时候不要使用；
- 与相似 Skill 的边界是什么。

描述写得很宽，Skill 会误触发；描述只写内部实现，模型不知道何时选择；多个描述高度相似，路由空间就会发生冲突。

## 五、两种相反的坏设计：薄壳森林与巨石 Skill

### 1. 薄壳森林

一个领域被拆成很多几乎没有独立逻辑的 Skill，每个只是把参数转给同一个隐藏的取数或处理中心。`[经验]` 命名来自一次内部能力目录审计，不是业界术语。

问题包括：

- 模型需要在多个薄壳中选择；
- 真正依赖藏在内部调用链；
- 权限和失败难以追踪；
- 多个 Skill 可能重复实现同一逻辑；
- 所谓组合发生在脚本内部，编排层无法观察。

如果多个 Skill 的差别只是一张表或一个参数，它们未必是不同能力。

### 2. 巨石 Skill

另一个极端是把一个领域的所有动作、数据源、异常和流程塞进一个巨大 Skill。`[经验]` 同上，属观察到的坏形态，不是通用分类。

它看似减少了路由入口，却带来：

- 任何子任务都要加载整份说明；
- 规则互相干扰；
- 无法独立测试和版本化；
- 一个小改动影响整个能力包；
- description 很难准确概括全部触发条件。

Skill 的合理颗粒度不应由数据库表、团队边界或已有脚本数量决定，而应由“用户要完成的连贯动作”决定。

判断是否该拆，可以问：

```text
这部分能否独立触发？
是否有独立输入、输出和失败语义？
是否能独立测试？
是否会在不加载其他部分时单独使用？
```

多数答案为否，可能不值得成为独立 Skill。

## 六、确定性逻辑不能因为放进 Skill 就交给模型

Skill 可以包含说明、参考资料和脚本，但不是所有步骤都应该由模型临场推理。

例如：

- 从当前对象取内部主键；
- 权限检查；
- 金额计算；
- 去重；
- schema 转换；
- 幂等处理；
- 必须执行的安全门禁。

这些动作应该放在代码或稳定 API 中。模型负责理解意图、选择流程和解释结果。

尤其要警惕不透明主键。让模型从多个相似长字符串中挑选一个，再逐字搬到下一次调用，既没有语义价值，又增加了静默命中错误对象的风险。代码可以直接引用字段，就不应该让 LLM 重新实现一次字符串搬运。

更可靠的分工是：

```text
LLM：理解用户想完成什么
Skill：提供这类任务的流程和领域约束
Tool：暴露必要的原子动作
API：提供稳定业务契约
代码：处理主键、权限、校验和确定性组合
LLM：解释最终结果
```

## 七、MCP 解决了接入标准，但没有消灭架构责任

MCP 的价值是标准化：能力提供方实现 Server，支持协议的客户端可以发现和调用工具或资源，减少每个 Agent 框架单独适配的成本。

但“已经通过 MCP 暴露”不能证明：

- Tool 名称适合模型理解；
- 参数 schema 足够清晰；
- 权限按最终用户身份执行；
- 工具颗粒度合理；
- 多个 Server 没有重复能力；
- 返回结果适合进入模型上下文；
- 高风险操作拥有确认边界。

标准化可以让坏设计更容易被大规模接入。因此，协议层之上仍然需要能力目录、权限模型、版本治理和评测。

## 八、四种让能力“需要时出现”的机制

### 1. 延迟加载工具

平时只保留少量索引信息，模型确认需要后再加载完整 schema。这样既保留总能力，又降低当前上下文负担。

### 2. 统一检索，保留来源命名空间

模型通常知道“我要完成什么”，未必知道能力属于哪个 MCP Server。默认先选 Server、再在 Server 内找工具，会增加一次不可靠映射。

更合理的是跨来源统一检索最相关能力，同时用命名空间解决重名、授权和溯源：

```text
意图 → 全局候选检索 → 相关 Tool
                      → 保留 server/tool 来源
```

只有明确知道来源时，才缩小到特定 Server。

### 3. 用 Skill 收敛知识，不隐藏执行链

Skill 可以把多步做法组织成一个可发现入口，但不应通过层层子进程把依赖藏起来。重要工具调用和业务动作仍应在编排或 trace 中可见。

### 4. 用子 Agent 隔离上下文，但不要把它当万能药

独立探索、资料收集、彼此无共享写状态的任务，适合放进子 Agent。它可以在自己的上下文中加载大量工具，只返回结构化结果。

紧耦合代码修改、共享状态频繁变化的任务，不适合为了“工具太多”盲目拆成多 Agent。否则上下文污染会变成交接污染。

## 九、一套能力治理清单

### 接入前

- [ ] 这个能力的消费者到底是代码、人还是模型？
- [ ] 是否已经存在等价 API、CLI、Tool 或 Skill？
- [ ] 为什么需要模型自主选择，而不是代码固定调用？
- [ ] 输入、输出、失败和权限语义是否稳定？
- [ ] 是否有至少三个真实评测场景？

### 设计时

- [ ] Tool 是否是一个清晰原子动作？
- [ ] Skill 是否对应一个连贯用户任务？
- [ ] description 是否写清“何时用”和边界？
- [ ] 确定性逻辑是否已经下沉代码？
- [ ] 高风险动作是否需要确认？

### 运行时

- [ ] 是否只加载当前任务相关能力？
- [ ] 相似工具是否发生误选？
- [ ] 工具返回是否携带过多无关内容？
- [ ] 调用链是否可追踪？
- [ ] 权限是否代表当前用户，而不是共享服务账号？

### 定期治理

- [ ] 删除无人使用和已禁用能力；
- [ ] 合并重复 Tool 和重复 Skill；
- [ ] 修正重名与描述冲突；
- [ ] 清理迁移到一半的双实现；
- [ ] 根据失败轨迹更新路由评测。

## 结语

Agent 能力架构的目标应当是：让模型在当前任务中看到足够少、足够清楚、足够安全的选择。把它理解成造一个无限扩张的工具箱，方向一开始就偏了。

API、CLI、Tool、MCP 和 Skill 各自解决不同层的问题。把它们分清之后，真正困难的工作才刚开始：确定职责、控制颗粒度、保护上下文、管理权限，并证明模型能够在正确时刻选中正确能力。

一句话总结：

> Agent 工程的核心只有一句：让正确能力在需要时出现，不需要时退出上下文。接了多少，只是手段。

## 证据边界声明

- **这是机制与结构论证，不是实验报告。** 核心主张（能力上限不等于实际能力；路由成本随「当前决策点同时可见的候选数与相似度」上升）由工程观察加第一性推理得出。本文**没有**做受控对照实验，也**没有**给出「接入 N 个工具导致准确率下降 X%」这类数字。你在别处看到这类数字，都不是本文的。
- **引用材料的支撑范围**：4 篇参考资料支持的是「协议层存在」「Skill 采用分层加载」这类事实，不支撑「接了就更好」或「接了就更差」的效果判断。
- **`[经验]` 的来源与局限**：薄壳森林、巨石 Skill、重复能力、半迁移这些形态，来自一次内部能力目录审计的观察。审计对象是私有目录，外部无法复核；换团队、换领域，具体比例与严重程度都会不同。它们是**观察到的坏形态**，不是统计结论。
- **适用边界**：本文讨论「由模型自主选择能力」的场景。如果调用路径由代码固定（workflow 而非 agent），第一节的路由税基本不成立，剩下的主要是治理税。
- **本文没做的事**：没有量化「候选数—误选率」曲线；没有实测延迟加载与统一检索的收益；没有比较不同模型对候选数量的敏感度差异。

## 下一步

- **想动手**：只做第九节「接入前」那五个问题。任何一个答不出来就先不要接，这一条能挡掉大部分后来的治理成本。
- **想核对依据**：参考资料里 4 篇都是一手文档，可逐条核；本文的判断句都带 `[经验]` / `[推测]` 标注，方便把「事实」和「作者主张」分开。
- **想改架构**：把「当前决策点同时可见的候选数」当成一个可测指标，先量出来再动手。指标不落地，讨论会停在「感觉工具太多」。
