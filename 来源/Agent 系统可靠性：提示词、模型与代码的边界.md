# Agent 系统可靠性：提示词、模型与代码的边界

很多 Agent 系统的事故，复盘时都会落到一句话：

> 模型怎么又没听提示词？

于是大家继续加提示词：必须、一定、不要、严禁、务必、再次强调。短期看，测试样例可能过了；过几天换一种问法、换一个模型版本、上下文长一点、工具多一点，问题又回来。

这类问题的根因往往不是“提示词写得还不够狠”，而是边界错了：我们把本该由代码保证的确定性，交给了一个概率模型去“尽量遵守”。

Agent 工程里最重要的分工不是“模型强不强”，而是：

- 哪些事适合交给 LLM；
- 哪些事只能交给代码；
- 哪些事提示词可以改善但不能保证；
- 哪些地方必须有不可绕过的硬闸门；
- 怎样把一个看似模糊的问题，改写成代码能兜住的形状。

本文试着给一套判断框架。

## 一、先看一个很小但很典型的坑

假设一个客服 Agent 接了“查客户档案”和“查工单”的能力。用户说：

> 帮我看看张伟这个客户最近的工单情况。

系统里叫“张伟”的客户有三个。Agent 需要先定位是哪一个张伟，拿到他的 `customer_id`，再用这个 id 去查工单。

结果它按名字搜，撞上三条记录，挑了错的那个张伟。更糟的是，它拿着错人的空工单，生成了一段看起来很像真的总结：

> 该客户近期工单较少，暂无明显异常。

复盘时，很容易把问题归因成“模型不够聪明”。但真正的问题不是模型智商，而是我们把一件不该交给模型的事交给了它。

这里至少混了三种不同性质的动作：

| 动作 | 性质 | 更适合谁 |
|---|---|---|
| 从用户话里识别“他想查客户张伟” | 语义理解 | LLM |
| 在多个同名客户里确定目标记录 | 规则、权限、上下文约束 | 代码或明确交互 |
| 从目标记录取 `customer_id` 再查工单 | 确定性数据访问 | 代码 |
| 把工单结果解释成人话 | 表达、总结 | LLM |

Agent 出错，是因为第二步和第三步滑到了 LLM 那边。

这就是很多 Agent 系统可靠性问题的原型：LLM 很适合做语义理解和表达，但它不适合承担“必须一字不差、必须唯一命中、必须可审计”的确定性搬运动作。

## 二、LLM 传参数不是不可靠，而是要分类型

说“不要让 LLM 传参数”是过度简化。LLM 每天都在给工具传参数，而且很多时候表现很好。

关键要分清两类参数。

| 参数类型 | 例子 | LLM 是否适合 |
|---|---|---|
| 生成型参数 | `name=张伟`、`city=上海`、`priority=high` | 通常适合 |
| 搬运型参数 | `customer_id=1000020698274`、`record_uuid=8f3a...` | 取决于风险维度 |

生成型参数来自语义理解。用户说“查上海的高优先级客户”，模型抽出 `city=上海`、`priority=high`，这是它擅长的。

搬运型参数不是理解，而是把上下文里已有的某个值原样拿到另一个地方。它看起来简单，其实很危险，尤其当这个值是不透明主键。

可以用五个维度判断搬运型参数是否适合交给 LLM。

| 维度 | 相对安全 | 高风险 |
|---|---|---|
| 语义 | `ORDER-SH-2026-001` 有业务含义 | `1000020698274` 无语义 |
| 长度 | 短 | 长 |
| 唯一性 | 当前上下文只有一个候选 | 多个相似候选 |
| 距离 | 值就在上一行 | 埋在几步前的大段列表里 |
| 可校验性 | 错了格式或含义明显不对 | 错一位也可能命中另一条真实记录 |

当一个参数同时满足“无语义、长、多个相似、跨上下文、错误难自检”时，它就不应该交给 LLM。不是因为模型一定会错，而是因为一旦错了，系统往往没有信号能发现。

一个订单号 `ORDER-SH-2026-001` 搬错了，至少看起来可能不对；一个 13 位纯数字 id 搬错一位，接口仍然可能返回 `success: true`，只是返回了另一个人的数据。

这类错误最可怕的地方不是失败，而是“成功地错了”。

## 三、为什么把 id 暴露给 LLM 反而更危险

有人会说：那就把 `customer_id` 明明白白放进上下文，让模型照抄，不就行了吗？

这恰好是更危险的一档。

如果 id 没进 LLM 视野，它最多按名字搜索，搜索失败或撞同名时，系统还有机会暴露出 `not_found`、`multiple_candidates` 这样的状态。

一旦 id 进了 LLM 视野，模型就可能去“使用”它。它可能抄错、截断、混淆，也可能在多个相似 id 里选错。更麻烦的是，错误 id 只要命中了另一条真实记录，接口会正常返回，后续链路会把这次错误当成成功处理。

所以，对不透明强主键，正确做法通常不是“让模型看清楚点”，而是“不要让模型碰它”。

上下文里应该给 LLM 看到的是它作答需要的语义字段：

```text
姓名：张伟
城市：上海
客户等级：VIP
最近工单：3 条
```

不应该为了省一段代码，把这类字段也交给模型搬运：

```text
customer_id: 1000020698274
internal_user_id: 9238471029384
record_uuid: 8f3a...
```

强主键应该留在确定性代码里流转。

## 四、代码为什么能把这件事做到 P=1

把“取 id 再查详情”交给代码，并不是因为代码更聪明，而是因为代码不用“猜”。

LLM 路径里有两个不稳定动作：

1. 在多个候选中判断哪个是目标；
2. 把目标记录的 id 原样搬到下一次调用。

代码可以把这两个动作改成零推理的数据访问：

```text
用户意图
  ↓
LLM 识别：用户想查“当前会话已选中的客户”
  ↓
代码：selectedCustomer.id
  ↓
代码：fetchTickets(customer_id)
  ↓
LLM：把工单结果解释成人话
```

代码路径并不需要“记住”那个 id，也不需要“复述”那个 id。它只是从结构化对象里取字段：

```ts
const customerId = selectedCustomer.id;
const tickets = await ticketService.listByCustomerId(customerId);
```

这里的关键差异是：LLM 在复制一个字符串，代码在引用一个值。

字符串复制有掉位、混淆、幻觉；字段引用没有。

所以，可靠 Agent 的设计原则不是“让 LLM 更努力地抄对”，而是“别让它抄”。

## 五、提示词不是栅栏，而是建议

上面讲的是“什么必须归代码”。接下来讲另一个常见误区：把提示词当成硬约束。

比如有人发现 Agent 有时不查数据库，直接凭上下文回答，于是在系统提示词里加一句：

> 回答前务必先调用查询工具。

测试几轮有效，于是上线。过一段时间，它又在某些问法下绕过了工具。

这不是偶然。提示词对 LLM 来说不是栅栏，而是建议。它能显著提高模型做某件事的概率，但不能把概率变成 100%。

这点在 Agent 场景里尤其明显，因为 Agent 不是单轮问答，它同时有：

- 长系统提示词；
- 多个工具描述；
- 多轮上下文；
- 用户临时补充；
- 工具返回内容；
- 中间状态压缩；
- 格式和业务约束叠加。

约束越多，模型越容易漏；上下文越长，指令越容易被稀释；工具越多，模型越可能走捷径或选错。

因此，更准确的说法是：

> 提示词降低失败率，代码消除可计算的失败。

这句话里有一个重要限定：可计算的失败。

不是所有问题都能被代码消除。比如“这段内容是否有误导性”“这个回复是否足够礼貌”“这条信息是否相关”，这些本质上是判断题，无法简单还原成一个确定性函数。它们只能用多层概率手段降低漏率。

但像“必须带某个字段”“id 必须来自当前记录”“没有查库结果就不能回答”“输出必须是合法 JSON”，这些是可以被代码检查或强制的，就不应该只靠提示词。

## 六、两问判断：提示词修，还是代码修

可以用两个问题判断一个约束该放在哪里。

第一问：能不能容忍偶尔漏一次？

- 能容忍：风格、措辞、优先级、偏好、解释方式，可以先用提示词。
- 不能容忍：权限、安全、强主键、金额、坐标、外部副作用、必须触发的动作，必须有代码兜底。

第二问：这条约束是顺着还是逆着 LLM 的省力路径？

- 顺水：模型本来就容易这么做，提示词只是提醒。
- 逆水：模型不这么做反而更省力，提示词就靠不住。

把两问合起来，可以得到一个简单矩阵。

| | 能容忍偶尔漏 | 不能容忍漏 |
|---|---|---|
| 顺水 | 提示词通常够 | 提示词为主，代码兜底 |
| 逆水 | 提示词为辅，重点监控 | 必须代码或硬闸门 |

什么是顺水？

例如“回答尽量简洁”“先给结论再解释”“如果数据很多，只总结最重要的三条”。这些约束顺着模型的表达能力走，提示词通常有效。

什么是逆水？

例如：

- 明明答案可以现编，却要求它必须先查工具；
- 明明可以按名字搜，却要求它必须使用权威 id；
- 明明可以输出一段自然语言，却要求它严格匹配复杂 JSON；
- 明明用户要求越权操作，却要求它拒绝并保持安全边界。

这些约束都逆着模型的省力路径。只写“务必”“严禁”“一定不要”，迟早会漏。

## 七、三类问题，三种处理方式

实际做 Agent 系统时，可以把问题分成三类。

### 1. 语义型：交给 LLM

语义型问题需要理解自然语言、归纳意图、组织表达。

例子：

- 用户到底想查什么；
- 这段工具返回应该怎样解释；
- 多个候选方案如何用人话对比；
- 面向非技术用户如何解释错误原因。

这些是 LLM 的强项。代码不应该试图用一堆正则完全替代它。

### 2. 结构型：提示词加校验

结构型问题不是模型不愿意做，而是它偶尔会漂。

例子：

- 输出合法 JSON；
- 字段名必须固定；
- 列表最多 5 项；
- Markdown 表格不能缺列；
- 函数参数必须符合 schema。

这类问题可以先用提示词改善，但要靠 schema、parser、validator、retry 或约束解码兜住。

区别在于：

- 提示词是在生成前请求它“尽量合法”；
- 校验是在生成后检查“不合法就不过”；
- 约束解码是在生成中让非法 token 根本出不来。

如果只是内部草稿，提示词可能够；如果下游程序要消费，就必须校验。

### 3. 权威型：归代码

权威型问题有唯一事实来源，或者可以还原成确定性计算。

例子：

- id 来自哪条记录；
- 用户有没有权限；
- 金额是否超过阈值；
- 坐标是否在围栏内；
- 是否已经查过必要数据；
- 是否允许执行删除、支付、发消息等副作用动作。

这类问题不要让 LLM “判断一下”。正确设计是让 LLM 提出意图，让代码做授权、取值、校验和执行。

LLM 可以说：

> 用户想查看当前选中客户的工单。

代码应该决定：

```text
当前用户是否有权限
当前会话选中的是哪个客户
customer_id 是多少
是否需要二次确认
是否允许调用查询接口
```

这不是保守，这是工程边界。

## 八、纵深防御：系统可靠，不等于模型可靠

很多团队追求“让模型 100% 听话”。这个目标本身就不对。

更合理的目标是：

> 允许模型是不完美的，但系统在关键事项上不能被它的不完美击穿。

这就是纵深防御。

以“回答前必须查库”为例，不应该只写一句提示词，而应该有两层：

```text
软层：提示词提示模型先查再答
硬层：返回前检查本轮是否存在对应查询结果
```

如果没有查询结果，系统可以：

- 阻止最终回答；
- 强制补查；
- 要求模型说明无法回答；
- 把状态标成未验证。

这样一来，模型“想偷懒直接答”也没关系，因为硬层会接住。

再看安全类问题。提示词可以告诉模型“不要泄露敏感信息”，但真正的系统还需要：

- 输入侧检测；
- 工具权限控制；
- 输出侧过滤；
- 操作前确认；
- 审计日志；
- 失败后的降级策略。

其中有些层是概率判断，有些层是确定性规则。多层叠加的价值不在于每一层完美，而在于它们抓的错误不同。

## 九、两条可靠性路线：叠软层，还是上硬闸

要让系统可靠，有两条路线。

| 路线 | 机制 | 适合什么 | 上限 |
|---|---|---|---|
| 叠软层 | 多个概率判断器互相补位 | 相关性、安全语义、内容质量 | 趋近 100%，但不是 100% |
| 上硬闸 | 确定性计算、schema、白名单、权限、状态机 | id、金额、权限、格式、范围、触发条件 | 可以做到系统层面的确定 |

很多争论来自把这两条路混了。

如果问题本质是判断题，比如“这段话是否有诱导性”，通常只能叠软层。你可以用规则、分类器、输出检查、人工审核降低风险，但很难宣称绝对不漏。

如果问题可以还原成确定性计算，比如“这个 id 是否来自当前记录”，那就不要叠一堆提示词和分类器。直接上硬闸：

```text
allowed_ids = current_record.related_ids
if requested_id not in allowed_ids:
    reject()
```

硬闸不是“更强的提示词”，而是把问题从概率空间移回程序空间。

真正的手艺在这里：把一个看似需要模型“更听话”的需求，改写成代码能检查的形状。

## 十、把模糊需求改写成可兜底需求

很多需求一开始长这样：

> Agent 不要乱编客户信息。

这句话太大，没法直接兜底。要把它拆成可执行的系统约束：

| 模糊说法 | 可兜底改写 |
|---|---|
| 不要乱编客户信息 | 回答中的客户字段必须来自查询结果 |
| 不要查错人 | 所有详情查询必须使用当前会话锁定的 `customer_id` |
| 不要越权 | 工具调用前统一做用户权限检查 |
| 不要没查就答 | 没有本轮查询记录时禁止生成事实性结论 |
| 输出要稳定 | 输出必须通过 JSON Schema 校验 |
| 不要误触发动作 | 有副作用操作必须二次确认并写审计日志 |

这张表背后的思想是：不要要求 LLM “永远做对”，而要把“做错”变成系统能观察、能阻止、能恢复的状态。

例如“不要查错人”不是靠提示词写：

> 请务必选择正确的张伟。

而是靠交互和状态机：

```text
1. 搜索名字，发现 3 个候选
2. 如果没有额外上下文可以唯一确定，要求用户选择
3. 用户选择后，把 selected_customer_id 写入会话状态
4. 后续详情查询只能使用 selected_customer_id
5. LLM 看不到也不搬运内部 id，只解释查询结果
```

这才是可靠性设计。

## 十一、为什么换模型会让提示词链路重新洗牌

很多团队还有一个误区：既然新模型更强，原来的提示词约束应该更稳。

不一定。

换模型不是把所有能力等比例提高，而是行为分布重新洗牌。新模型可能更会推理，但也可能更爱自作主张；可能格式更稳，但工具调用更懒；可能更安全，但误拒更多；可能更愿意遵守系统指令，但对旧 few-shot 的风格学习变弱。

对 Agent 来说，最容易漂的是这些维度：

- 工具调用积极性：该查不查，或不该查乱查；
- 输出格式：字段缺漏、额外包 Markdown、键名变化；
- 冗长度：多解释、多做一步、多触发副作用；
- 拒绝边界：误拒或误答；
- 长上下文注意力：旧约束被新消息稀释；
- 补丁型提示词：针对老模型缺陷写的纠偏句，在新模型上可能变成干扰。

所以，关键路径不要绑定在“当前模型刚好听这句提示词”上。至少要做到：

- 生产环境钉模型版本，不静默使用 `latest`；
- 建小而真实的回归 eval；
- 换模型时比较工具调用率、格式失败率、拒答率；
- 重新审查旧提示词补丁；
- 把强主键、权限、安全、副作用交给代码。

模型可以升级，硬边界不能跟着漂。

## 十二、一套落地检查清单

设计或评审一个 Agent 功能时，可以按下面的顺序问。

第一，这一步是在做语义理解、表达，还是在做权威事实搬运？

- 语义理解和表达可以交给 LLM；
- 权威事实搬运优先归代码。

第二，这个值错了以后，系统能不能自检？

- 能自检，可以用校验和重试；
- 不能自检，尽量不要让 LLM 生成或搬运。

第三，是否存在多个相似候选？

- 有，就不要让 LLM 靠名字或记忆选主键；
- 要么让用户确认，要么用明确规则锁定。

第四，这条约束能不能容忍偶尔漏？

- 能，提示词通常够；
- 不能，必须有硬兜底。

第五，这条约束是顺水还是逆水？

- 顺水，提示词收益高；
- 逆水，提示词只能当辅助。

第六，能不能还原成确定性计算？

- 能，就写成代码、schema、状态机、权限检查或白名单；
- 不能，再考虑多层概率防御和人工审核。

第七，失败是否可观察、可恢复？

- 不要静默失败；
- 不要把未验证结果包装成确定结论；
- 要记录关键工具调用、校验失败和拦截原因。

## 十三、一个简化架构范式

可靠 Agent 往往不是“一个大模型直接管到底”，而是下面这种夹心结构：

```text
用户输入
  ↓
输入规范化与权限检查（代码）
  ↓
LLM：理解意图、选择下一步
  ↓
工具层：查询、计算、执行（代码）
  ↓
结果校验与状态更新（代码）
  ↓
LLM：解释、总结、提出下一步
  ↓
输出校验与安全闸门（代码）
  ↓
用户看到的结果
```

LLM 在中间做软活，代码在两端和关键节点做硬边界。

这个结构并不是不信任模型，而是尊重模型。让模型做它擅长的事：理解、归纳、表达、提出候选方案。让代码做它擅长的事：取值、校验、授权、状态机、不可绕过的执行约束。

好的 Agent 工程，不是把 LLM 当成万能后端，也不是把 LLM 关进只能填空的笼子。它是在概率能力和确定性系统之间建立清晰契约。

## 十四、常见反模式

### 反模式 1：用更强提示词替代权限检查

写“不要越权访问用户数据”不等于做了权限系统。权限必须在工具调用层检查，不能由模型自觉遵守。

### 反模式 2：把主键当文本交给模型搬运

只要主键无语义、长、候选多、错了难自检，就应该从模型上下文里拿掉，让代码在结构化数据里流转。

### 反模式 3：没有查到数据也允许模型生成事实性回答

工具返回空、失败或未调用时，最终回答应该显式标注不确定，或被系统阻止。

### 反模式 4：把 JSON 稳定性完全押给提示词

只要下游程序要消费，就必须有 schema 校验。提示词不能替代 parser。

### 反模式 5：工具越多越好

工具越多，模型选择空间越大，注意力越稀释。主 Agent 只应看到当前任务必要的能力；复杂工具组可以用 skill、子 Agent 或延迟加载隔离。

### 反模式 6：测试只测 happy path

可靠性问题通常出现在同名、空结果、权限不足、工具失败、上下文很长、用户换说法、模型升级之后。只测最顺的一条路径，等于没测边界。

## 十五、总结

Agent 系统的可靠性，不来自“提示词足够严厉”，也不来自“模型足够聪明”，而来自正确分工。

LLM 适合做：

- 意图识别；
- 语义归纳；
- 候选方案生成；
- 面向人的解释和总结。

代码必须负责：

- 权限；
- 状态；
- 主键；
- 金额；
- 坐标；
- schema；
- 副作用；
- 可审计的硬约束。

提示词的价值是把模型推向更好的行为分布；代码的价值是把关键错误挡在系统边界之外。

所以，真正的工程判断不是“这句提示词怎么写得更强”，而是：

> 这件事到底应该被模型理解，还是应该被系统保证？

一旦能回答这个问题，很多 Agent 可靠性设计都会变得清楚。
