# AI 让“看起来正确”变得廉价：从似真产出到证据化工程

过去做软件，产出本身就是一种稀缺能力。

一个能运行的功能、一份结构完整的方案、一段像样的总结，都需要人投入时间。因为生产成本高，“做出来了”和“基本做对了”虽然不是一回事，通常也不会离得特别远。

AI 改变了这层关系。

现在，一段格式漂亮的 JSON、一个逻辑完整的方案、一句自信的“已经完成”、一份读起来毫无障碍的 PRD，都可以在几秒内生成。AI 把“看起来正确”的成本压得很低，却没有按同样比例降低“证明它真的正确”的成本。

这带来一种比明显报错更危险的失败：

> 系统没有失败，而是成功地产出了一个错误结果。

它可能通过 schema 校验，接口返回 `success: true`，页面正常展示，文字也足够流畅。直到有人用真实数据、真实链路或真实业务边界去核对，才发现整个结论建立在错误前提上。

AI 时代的工程瓶颈正在移动：从“能不能产出”，转向“能不能低成本、系统地分辨似真与真”。

对实际团队而言，这不是抽象的“AI 幻觉”问题，而是三个会直接消耗工程时间的问题：接口和 hook 的能力靠猜、批量产出用数量冒充质量、Agent 用完成声明替代可复核结果。本文不讨论如何让模型更会写，而讨论如何让错误结果无法只凭外观过关。

### 读完可以直接拿走什么

- 一个判断集成点是否真的可用的最小探针；
- 一组区分 raw、valid、grounded、useful 的产出指标；
- 一条从需求、实现到生产抽检的证据链；
- 一个决定何时用代码、模型判别或人工抽检的门禁分层。

## 一、一次看似简单的功能为什么会两次推倒重来

考虑这样一个功能：Agent 完成一轮任务后，自动给用户生成一张总结卡。

第一版方案把生成逻辑挂在一个工具调用完成后的 hook 上。这个位置名字合理、触发稳定，也确实能拿到工具返回，于是系统很快“成功出卡”。

真正抓取运行轨迹后才发现：这个 hook 只能看到当前工具的结果，看不到整轮任务的最终回答，也看不到同一轮其他工具的完整信息。它生成的不是总结，而是“电影演到一半写出的影评”。

第一版整体作废。

第二版把生成位置移到一轮结束之后，终于能拿到完整结果。批量运行时，系统产出了 14 张卡。单看数量，功能已经完成；但按时间范围、数据充分性、证据一致性和展示价值筛选后，真正适合给用户看的只有 5 张。

其余结果包括：

- 把旧数据写成近期变化；
- 把一批明细描述成趋势；
- 查询失败后仍然生成一张“暂无异常”的卡；
- 数据不足，却用流畅语言补出结论。

两次翻盘表面上分别是集成点选错和质量不足，底层却是同一个问题：

> 团队在关键节点接受了一个“足够像真的替身”，没有继续追问真实能力和真实证据。

## 二、四种最危险的“正确替身”

似真并不是随机出现的。在 AI 系统里，它经常藏在四类位置。

### 1. 状态字段替代真实成功

最外层的 `success`、`done`、`completed` 很容易被当成结论。

但一个多层系统可能出现这样的返回：

```json
{
  "status": "success",
  "data": {
    "tool_result": {
      "message": "upstream timeout"
    }
  }
}
```

外层只表示“流程走完了”，内层才表示“业务动作是否成功”。异常可能被捕获，工具调用可能正常结束，HTTP 也可能返回 200，但这些都不能证明用户要的结果已经成立。

因此，状态字段只能作为线索，不能独立充当业务事实。判断成功必须深入到产生价值的那一层：数据是否存在、时间范围是否正确、关键动作是否真正执行、结果是否满足业务约束。

### 2. 原始产出替代有效产出

“生成了 14 个结果”描述的是吞吐量；“其中 5 个可用”描述的才是质量。

生成系统天然倾向于把“我产生了一个对象”当成“我完成了任务”。如果验收指标只统计原始产出数，系统会被激励去制造更多形式完整的垃圾。

更合理的指标至少要区分：

```text
raw output      原始产出
valid output    通过确定性规则
grounded output 有足够证据支撑
useful output   对用户确实有价值
```

这几个数字之间的差距，比总产出数更能说明系统质量。

### 3. 名称和先验替代真实能力

`post_tool_use`、`after_action`、`on_complete` 之类的名称，会让人自然推断它们“应该”能拿到完整上下文。LLM 也会根据见过的其他框架，生成一个听起来合理的能力说明。

但集成点的能力是经验问题，不是语言推理问题。

“整个系统里存在这份数据”不等于“这个回调会把数据传给你”；“大多数框架这样设计”也不等于“当前仓库如此实现”。答案只能来自：

- 派发代码；
- 函数签名和真实载荷；
- 一次最小探针；
- 一条完整运行轨迹。

在一个未经验证的 hook 上继续设计，后续方案越精致，沉没成本越高。

### 4. “做完了”替代可验证完成

AI 很擅长生成任务结束时应有的语言：修改完成、问题已解决、测试应该通过。

这类表述可能描述的是“它执行了修改动作”，也可能只是“它认为方案足够合理”。两者都不等于功能真的工作。

同样，PRD 里的“生成一张高质量总结卡”读起来人人都懂，却没有定义：

- 什么情况下不应该生成；
- 多长算过长；
- 什么数据足以支撑趋势判断；
- 哪些结论必须带时间和来源；
- 失败时应该沉默、降级还是提示。

“完成”和“理解”如果没有可观察的下落，都只是漂亮的状态描述。

## 三、为什么“以后仔细一点”解决不了问题

发现这些风险后，最自然的反应是：以后多检查一下。

这不是可靠的工程方案。

一方面，模型不会因为上一次被纠正，就永久形成新的行为。没有进入系统提示、项目指令、测试或代码门禁的纠正，换一个会话后很可能重新发生。

另一方面，人也会忘。系统在大多数时候表现正确，反而会培养自动化偏见：工具越可靠，人越少核对；越少核对，偶发的高置信错误越容易穿过整条链路。

可靠性不能依赖每个人在每一次执行中都保持警觉。正确方向是把判断固化成机制：

```text
靠记得检查
    ↓
每次自动检查
    ↓
检查不通过就无法继续
```

工程的价值不只在于降低错误概率，还在于让某些错误没有机会静默通过。

## 四、四种把“证真”变成机制的方法

### 1. 在集成点上先放探针，再做设计

如果一个功能依赖 hook、回调、消息事件或框架生命周期，先写一个不承担业务逻辑的最小探针：

```text
收到哪些字段？
调用发生在什么时候？
同一轮会触发几次？
异常和取消时是否触发？
能否看到最终结果？
```

先记录原始载荷和时间顺序，再决定是否适合作为集成点。

这里最重要的纪律是：不接受“应该能拿到”，只接受“这段代码传递了这些字段”或“这次运行实际收到这些内容”。

### 2. 在产出边界设置质量门禁

门禁不是 LLM 专属保险。规则系统、模板系统和统计系统同样可能在错误输入上稳定地产出错误结果。

只要同时满足以下三点，就应该考虑门禁：

1. 结果由系统生成或推导；
2. 结果会展示给用户，或驱动下游动作；
3. 输入本身不能天然保证结果有效。

门禁最好分层：

| 层级 | 检查内容 | 适合方式 |
|---|---|---|
| 结构 | schema、必填字段、类型 | 代码 |
| 范围 | 长度、枚举、时间窗、数值范围 | 代码 |
| 证据 | 结论能否对应来源，关键数据是否存在 | 代码优先，必要时模型判别 |
| 语义 | 是否误导、是否过度断言 | 模型判别或人工抽检 |
| 业务 | 是否值得展示，失败应否降级 | 产品规则与代码 |

schema 通过只能证明“可以解析”，不能证明“事实正确”。反过来，门禁也不是越严越好。过度拦截会把系统变成沉默机器，因此要同时观察误放和误杀。

### 3. 把完成条件写成可独立检验的清单

“标题简洁”无法验收；“标题不超过 32 个字符，且不能通过截断破坏语义”可以验收。

一个好的完成条件应该让第三方无需理解作者意图，也能回答“过还是不过”。例如：

- 必须运行哪些测试；
- 哪些输出字段必须存在；
- 哪些负面场景不得产生结果；
- 数据时间窗如何判断；
- 什么证据需要保留；
- 哪些结果必须人工确认。

让“完成”从一句报告变成一组证据：测试输出、运行截图、trace、实际响应或可重复命令。

### 4. 让验证者拥有独立视角

自查的问题不只是态度。创作者已经接受了自己的前提，复查时容易继续沿用同一套解释。

更可靠的方式是让验证者从外部证据重新建立判断：

- 新会话读取 `git diff` 和测试结果；
- 独立评审者对照原始需求逐条检查；
- 模型读取原始记录，而不是作者自己的总结；
- 关键高风险结果接受人工抽检。

重点不是“再问一次”，而是改变验证者看到的信息和所处的位置。

## 五、一条完整的证据链应该长什么样

四种机制不是独立的补丁。它们可以组成一条从需求到生产的证据链：

```text
需求
  ↓ 写成可验收条件和负面用例
设计
  ↓ 用探针确认集成点真实能力
实现
  ↓ 代码测试、schema 与业务门禁
交付
  ↓ 独立验证实际产物
生产
  ↓ trace、抽样评估、失败样本回流
```

每一层都回答不同的问题：

| 层 | 要证明什么 |
|---|---|
| 需求 | 团队对“正确”是否有同一个定义？ |
| 设计 | 方案依赖的能力是否真的存在？ |
| 实现 | 代码是否满足确定性约束？ |
| 交付 | 实际结果是否符合需求，而不只是改了代码？ |
| 生产 | 真实输入分布下是否仍然可靠？ |

如果其中一层只能提供一句“应该没问题”，证据链就在那里断了。

## 六、AI 时代工程师的价值正在换位置

AI 没有让工程能力失去价值，只是改变了稀缺环节。

当代码、文案、方案和测试样板都能迅速生成，单纯“做出一个东西”不再足以构成高质量交付。更稀缺的是：

- 找到似真与真最容易分家的位置；
- 把模糊的“好”改造成可执行标准；
- 为概率组件设计确定性边界；
- 保留能被第三方复核的原始证据；
- 让一次事故变成以后每次都会执行的门禁。

这不是对 AI 更不信任，而是把它当成真正的生产组件：既利用它的生成能力，也承认它的输出需要被验证。

一句话总结：

> AI 让产出变得便宜，所以工程价值越来越集中在判真假；而判真假不能靠每次自觉，必须靠证据和机制。
