# 读完代码，还不算了解这个系统：陌生后端的事实核验七步法

> 2026-10-28 · 方法指南 · 面向接手、对接和评估陌生后端的工程师与技术负责人  
> [离线讲解版](../阅读/讲解-09-项目事实核验.html) · [阅读目录](../阅读/index.html)

AI 可以快速从目录与代码写出架构说明，但它通常拿不到全部运行事实。**读码建立候选地图，受控观察确认局部事实，运行身份与构建记录反查实际部署；最终只把证据够得着的结论写成事实。**

本篇从原有“读码、实测、反查”方法重构七步，而不是把项目命令批量换名。重点不是多跑几个探针，是每个结论都有对象、环境、时间和支持范围。没有运行权限仍可以产出有用的结构说明，只是必须标清哪些尚未验证。

<a id="repo-case"></a>
## 一、三个看似合理的答案，为什么都可能答过头

**构造案例**：接手一个导出服务，Agent 找到数据库配置，看到 API 文档返回 200，又从镜像标签里截出一个 Git 哈希，于是写下：“这个服务调用该数据库所属后端；所有接口可用；线上来自 main 分支。”

三句都超出了证据。共享数据库不能证明 API 调用；文档可获取不能证明每个操作成功；一个提交可能被多个分支包含，镜像标签也不能单独证明实际运行内容。

这正是事实摸底容易失败的地方：命令是真的，返回也是真的，**从返回到结论的跨越没有被审查**。源稿里也有这类过强推断。本篇保留三段论，修正其证据等级；不把旧稿的 verified 标签当作每句话正确的保证。

<a id="repo-ledger"></a>
## 二、先建立四个栏位，再开始七步调查

把结论分成四栏：声明、观察、推断、未知。

| 类别 | 示例 | 写作纪律 |
|---|---|---|
| 声明 | 配置模板声明端口为 8080 | 注明文件与版本，不冒充运行值 |
| 观察 | 某时刻某环境返回的健康检查为 200 | 保留对象、时间与结果范围 |
| 推断 | 两个组件可能共享数据源 | 写依据、替代解释与下一步证据 |
| 未知 | 无权限读取实际 Pod 镜像身份 | 写缺口及它影响的决策 |

“实测”不是结论的万能前缀。TCP 连接成功是网络可达的观察，不是登录成功；登录成功不是有权读目标表；查到目标表也不是业务功能正确。每一次观察都需要写明测了哪一层。

建议每条重要记录采用：`问题 → 对象/环境/时间 → 证据位置 → 观察结果 → 当前结论 → 不能证明什么 → 下一步`。以下七步每一步都往这张账里填，而不是等最后再给整篇说明贴一个“已验证”。【方法设计】

<a id="repo-steps"></a>
## 三、七步法：从声明地图到实际运行身份

### 1. 锁定调查对象与证据时点

先写仓库、当前提交、工作区是否有未提交修改、调查环境，以及要支持什么决策。准备估算迁移成本，与准备排查一次故障，需要的覆盖面不同。

```bash
git rev-parse HEAD
git status --short
git rev-parse --is-shallow-repository
```

普通 `git clone` 不能一概写成默认浅克隆；`--depth` 等选项才会创建受限历史。浅仓库会影响依赖缺失祖先的分析，但不是所有历史结果必然错误。先检查；确需完整历史时再按实际权限与网络条件补取。参见 [Git clone 官方文档](https://git-scm.com/docs/git-clone)。

### 2. 读码画出声明地图

从构建文件、启动入口、路由、配置加载逻辑和部署清单，整理语言依赖、模块、候选数据源、接口与调用者。搜索优先输出文件路径与字段名，避免把配置值和秘密直接打印到终端或写入文章。

要查配置的**优先级**：默认值、环境变量、挂载配置、命令行参数、动态配置可能相互覆盖。未被注释的配置只说明它在文件里启用，不证明它最终生效。地图上暂时写“声明连接 A”，留待运行证据确认。

### 3. 逐层观察数据源，分清无权查看与不存在

在已授权的目标上，先确认连接与身份，再按业务需要查看可见对象。以 PostgreSQL 为例，`information_schema.tables`可帮助查看当前身份可见的表与 schema；**查不到不等于物理不存在，也可能是权限或环境不对。** 精确语义参见[官方表视图文档](https://www.postgresql.org/docs/current/infoschema-tables.html)。

记录逻辑库、实际端点、当前身份可见范围、业务对象与数据新鲜度。不同地址可能是同一集群的代理或副本，同名数据库也可能属于不同集群；只看 IP 或库名都不足以判定数据血缘。

“只读”也不自动意味着低负载。大表全量计数、昂贵查询可能影响服务。按需要使用已知成本的元数据或统计估计，并标明估算而非精确值；不要为了把表格填满而扫描全部数据。本文不提供真实连接信息，也不要求运行任何生产探测。

### 4. 对照接口声明、暴露与真实业务行为

至少分开三份清单：代码里定义的操作，目标实例公开描述的操作，已经验证过的操作。OpenAPI 文档可能隐藏接口、被网关过滤、与实例版本不同；它是声明证据，不是全量可用性证明。

原稿用 `sum(len(item) ...)` 计数会把路径级参数、摘要等当成操作。下面的离线统计只数 OpenAPI 3.1 的 HTTP 方法，并明确其局限：

```python
import json
from pathlib import Path

spec = json.loads(Path("openapi.json").read_text())
methods = {"get", "put", "post", "delete", "options", "head", "patch", "trace"}
paths = {p: item for p, item in spec.get("paths", {}).items()
         if p.startswith("/")}
operations = [(p, method) for p, item in paths.items()
              for method in methods if method in item]
print({"described_paths": len(paths),
       "described_operations": len(operations)})
```

该示例只用于**已取得的 OpenAPI 3.1 JSON**，不解析 `$ref`，不包含 webhook，不代表其他版本或运行时全部接口。Path Item 除 HTTP 方法还有其他字段，可对照[固定的 3.1.1 规范](https://spec.openapis.org/oas/v3.1.1.html#path-item-object)。

验证业务时，只选择已授权且副作用明确的操作。不能因为方法叫 GET 就假定绝无写入；文档返回 200 也只能证明该响应在那个时刻取得成功。

### 5. 用运行证据核对调用与数据依赖

配置相同，可以支持“可能共享数据源”，不能支持“A 调用了 B 的 API”。后者需要调用代码与运行配置相符，并最好有目标时段的请求记录、关联 ID 或分布式 trace。

同样，没有看到请求也不自动证明从不调用：可能观察窗口不够，或埋点与采样不完整。写清证据强度。若实际是两个组件绕过服务共同直连数据库，应按“共享库访问”记录，而不是把它画成服务调用箭头。

### 6. 反查运行制品与构建来源

先找实际运行实例的镜像身份，再找镜像制品与构建记录的关联，最后确认构建对应的源码 revision。部署清单是期望态，运行实例还可能处于滚动更新中。

[Git 的 `--contains`](https://git-scm.com/docs/git-branch)只返回包含指定提交的分支，不回答镜像由哪个流水线构建。输出多个分支完全正常。标签也可能被重新指向；[Kubernetes 镜像文档](https://kubernetes.io/docs/concepts/containers/images/)说明 digest 用于标识具体镜像版本。

```text
实际运行实例 → 镜像身份/digest → 构建制品与流水线记录 → 源码 revision
                                  └─ 还需核对配置、挂载与发布时点
```

即使找到源码 revision，配置差异也能改变行为。若构建来源不可核实，就写“已知运行镜像，源码来源未核实”，而不是从分支名猜出一个答案。

### 7. 形成能支持决策的事实底账

最终文档可以按入口、数据源、接口、业务路径、运行制品、未知与影响组织。重要的不是固定段数，而是负责人能看出：哪些结论足以支持当前决策，哪些仍会改变工期、风险和方案。

例如：“目标环境接口描述可读取，但关键鉴权路径未验，因此可评估接口范围，暂不能承诺迁移后业务可用。”这是有用的调查结果，不是未完成的尴尬附注。复查时优先补会改变决策的未知。

<a id="repo-example"></a>
## 四、把开头的案例重写成一份可信记录

继续同一**构造案例**，以下是应有的结论强度，不是实际测量：

| 取得的证据 | 可写结论 | 还差什么 |
|---|---|---|
| 两个组件配置同一逻辑库 | 存在共享库依赖的候选关系 | 实际解析端点、访问身份与运行记录 |
| `/openapi.json` 返回描述 | 该环境暴露了这份接口声明 | 关键业务操作、鉴权、网关与版本差异核对 |
| 提交被 main、release 同时包含 | 两个分支的历史均包含该提交 | 镜像构建来源及运行制品身份 |
| 健康端点响应成功 | 本次健康端点检查通过 | 数据依赖与业务目标是否成功 |

这种写法看上去少了“全都查清楚”的气势，却更容易指导下一步。事实底账的价值是减少错误承诺，不是制造一张每格都填满的表。

<a id="repo-branch"></a>
## 五、调查停止条件：按决策需要，而不是按命令数量

如果只是做结构导读，没有生产访问也可以交付声明地图与未知清单；如果要承诺生产迁移，就不能拿声明地图代替关键业务验证。对纯库、离线算法仓库或没有部署态的工具，应缩减运行相关步骤。

环境拒绝访问时，标清“无法从当前身份核实”。不能把权限拒绝写成对象不存在，也不能把绕过授权换一个入口当作默认排查方式。可由获授权的维护者提供最小证据，再记录来源与时间。

健康检查的含义同样取决于探针设计。Kubernetes 的存活、就绪与启动探针各有职责；一次成功不构成全部业务正确性的结论。参见[官方探针文档](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)。

结束前问三件事：当前决策依赖哪些事实；每个事实是否有足够强的证据；剩下的未知是否会改变决策。如果不会，继续穷举全部表与接口可能没有收益；如果会，就不能用一句“基本跑通”掩盖缺口。

<a id="repo-boundary"></a>
## 六、证据边界与本文的增量

原始素材来自多个后端摸底过程；本轮核对的是这些文档与公开机制说明，**没有连接生产数据库、调用内部服务或重跑部署调查**。原有事故和数量不作为本篇已独立验证的实测成绩。

公开来源分别支撑 Git 历史选项、OpenAPI 字段、PostgreSQL 可见性以及 Kubernetes 镜像与探针语义；构造案例用于解释推理，不能作为发生频率的证据。七步组织与四栏底账是本文的综合方法，尚无量化效率提升实验。

它对原稿的增量在于：把“实测才算真”改为**每次观察只承担其支持范围内的结论**，并给“调用关系”和“运行源码”增加证据链。这样，AI 生成的项目说明才能从流畅叙述变成可审查的调查结果。

与现有《越聊越浅》侧重上下文管理不同，本篇不讨论协作记忆；与《证据化工程》不同，本篇具体处理陌生后端的配置优先级、接口声明、依赖关系和运行身份。完整删改记录见[本轮复核](../复核/2026-10-28-Top3选题与核验.md)。
