Claude Code 与 Codex，到底选哪个？

一句话核心观点：单次通过率衡量的是终点，协作可靠性衡量的是到达终点的路上你要付出什么——两者解决率几乎打平（78.4% vs 77.4%），但失败动作差 2.4 倍，公开证据初步支持 Claude 系更适合"边聊边改"的真实协作。

为什么值得读：这是一篇证据评审型调研——不靠个人安利，而是把两篇公开论文、2500 条轨迹数据和 7 个可点击核实的 GitHub issue 摆在桌面上，逐条说明每类证据能证明什么、不能证明什么。所有关键数据都在 2026-10 逐一核实过，复核路径写在文末。

⏱ 30 秒版

  1. 表面矛盾：Codex 在 SWE-bench 类基准上解决率还略高（78.4% vs 77.4%）。那为什么还判 Claude 更好？——因为通过率相同，路径可以完全不同。
  2. 过程证据：TraceProbe 分析 2500 条轨迹发现，Codex 的失败动作占比 8.0% vs Claude 的 3.3%（约 2.4 倍），有害动作 0.10 vs 0.07——它用更多试错换到同等结果。
  3. 协作证据：SWE-Together 首次统计"用户要纠正几次"，发现模型越强用户纠正越少（相关性 −0.92）；Claude Opus 4.8 以 63% 通过率 + 最少纠正（1.38 次）双料第一。
  4. 失败模式：7 个已核实的 Codex issue 表明，长会话压缩后"累计约束碎裂"真实存在——它能复述任务大概，却悄悄丢掉你几轮前定下的规则。
  5. 诚实的边界：这些是预印本和案例证据，不是定论；本文的判断是"初步支持"，复核数据和路径全部公开。

情境 S选编码 Agent 的人都在看同一类数字：SWE-bench 解决率。Codex 在这些榜上很强，Claude Code 也强，分数咬得很紧。

冲突 C但真实用过的人体验差别很大：一个像靠谱的搭档，你说一半它懂一半；另一个单兵作战凶悍，长任务里却越干越偏——你让它改个按钮，它把后端也"顺手"重构了。分数一样，体验为什么两样？

问题 Q排行榜到底漏掉了什么？"体验好"是玄学，还是有证据？

答案 A排行榜测的是"终点对不对"，漏掉了"路径的成本"。本文用三类公开证据（受控评测 + 过程诊断 + 失败案例）说明：协作场景下真正该比的是任务模型稳不稳定、你要纠正多少次、失败后能不能便宜地爬出来。

贯穿全文的类比：两个装修队，都声称懂"北欧风"

生活类比：你雇两个装修队，都说要做"北欧风"。A 队开工前先复述："我理解是浅色木地板、无主灯、收纳全部隐藏——对吗？"做完你基本满意，小修两处就好。B 队开局也利索，但干着干着墙刷成了米黄（"暖一点更显质感嘛"），柜子装满了整面墙（"北欧也流行收纳呀"）——每一步它都有自己的理由，最后"完工"了，可验收时几乎每间房都要返工。
工程锚点：两个队的"最终完成度"可能都是 78%——但 A 队的问题是低成本的局部修正，B 队的问题是目标表征本身漂了：它不是手艺不行，而是它心里那版"北欧风"已经和你说的不是同一个东西。编码 Agent 的"任务模型"就是这版"北欧风"：多轮对话、上下文压缩、连番纠正之后，它还记不记得你最初到底要什么。
类比的边界：碎裂的是目标表征，不是沟通态度——B 队不是不认真，它的"理解"在你看不见的地方悄悄换代了。另外装修队会主动跑来问你，而模型不一定会：所以工程上要把"先复述理解再动手"从美德变成机制。

核心证据：终点相同，路径不同

把 TraceProbe 的数据画成一条"到达终点之路"：横轴是任务进度，纵轴是"离正确目标的距离"。两个 Agent 最终都到了（解决率 78.4% vs 77.4%），但一条线平稳收敛，另一条线反复冲进失败区再爬出来。

证据出处：TraceProbe（arXiv 2607.06184，2026-07-07），2500 条轨迹、五个生产设置，数据与代码公开（Zenodo DOI 10.5281/zenodo.20789918）。SWE-Together（arXiv 2606.29957）则从 11,260 条真实会话筛出 109 个多轮任务，首次把"用户纠正次数"列为主要指标：模型越强纠正越少（Pearson −0.92），Claude Opus 4.8 以 63% 通过率 + 1.38 次纠正双第一。

第二个证据：长会话里，目标表征会悄悄碎裂

比"做错"更危险的是"忘了自己在做什么"。7 个可点击核实的 Codex issue 描述了同一条退化路径：约束一层层加上去，上下文一压缩，只剩一份不完整的摘要——它还能复述"大概要做什么"，但执行时遗漏你几轮前定下的硬规则，甚至复活你明确否决过的方案。你每纠正一次，它又可能把最新一句话当成全部目标。

证据可信度分层：这篇文章的每个判断踩在哪层？

证据评审和"听个瓜"的区别，在于分层。本文的证据金字塔从下到上：案例（证明存在）→ 过程诊断（证明分布差异）→ 受控评测（证明相关性）→ 顶部空缺（尚无成对实验）。结论的强度刻意跟金字塔对齐。

选型原则一句话：别问"谁的分数高"，问"它跑偏的时候，你把它拉回来的成本是多少"。

对照一下就用得上：把"任务模型稳定性"当作选型面试题——长会话压缩后让它复述当前约束清单，对照你自己的记录；给一次局部纠正，看它是增量更新还是整段覆盖；故意给一个做不了的任务，看它解释失败时暴露的是"动作流水账"还是"可编辑的理解"。三个答案比任何排行榜都更接近你将来的真实体验。

面试官可能会追问

Q1：109 个任务、7 个 issue，样本量这么小凭什么下结论？
直接回答：如果只有 SWE-Together 一项研究，确实不够下任何结论。这个判断的成立方式是三层独立证据交叉：受控评测（109 任务）给出"能力与纠正量强负相关（−0.92）"的方向；过程诊断（2500 条轨迹）在同解决率下测到失败动作 2.4 倍的分布差；7 个 issue 只负责证明"约束碎裂这种失败真实存在"。三者测量方式、数据来源、偏差结构都不同，却指向同一方向——这比任何单一大样本更有说服力。同时结论强度被刻意限定为"初步支持"，并写明了复核路径：数据全部公开，欢迎重算。
Q2：解决率就差 1 个百分点，你怎么说一个是"平稳收敛"、一个是"反复试错"？
因为过程指标不在排行榜里，但在轨迹里。TraceProbe 的实测：Codex 失败动作占比 8.0% vs Claude 3.3%，有害动作 0.10 vs 0.07，工具成功率 91.9% vs 96.7%。要诚实的是：这是模型与框架同时变化的混合证据，只能支持"组合设置"层面的比较；TraceProbe 自己也指出 Codex 的保留动作占比反而更大。所以精确的说法是"失败动作与有害动作两个维度更高"，而不是笼统的"Codex 更乱"。
Q3：你自己是不是用惯了 Claude，确认偏差怎么排除？
排除不了，只能管理——这正是深入版专设"用户观察方法说明"的原因：观察约一年、数十次长会话、非系统化记录，明确列出四类已知偏差（确认偏差、记忆偏差、版本漂移、任务难度不平衡），并把用户观察的功能严格降级为"提出研究问题"。成立与否交给可复核的公开证据检验：如果 SWE-Together 没有测出纠正量差异、TraceProbe 没有测出过程分布差异，我的个人体验就只能算轶事。
Q4：这些都是预印本和企业自报 issue，可信吗？会不会半年后就过期？
两层回答。可信度：SWE-Together 与 TraceProbe 方法、代码、数据全部公开，任何数字都能重算；issue 有完整复现步骤和日志，我核实过全部 7 个（2026-10-16）。时效性：具体版本号（Opus 4.8、GPT-5.4）当然会过期，但这篇要保留的不是排名，而是方法论——"通过率掩盖过程差异"这个命题在模型换代后依然可测、可证伪。METR 页面 2026-09 已声明不再活跃更新，这也如实写进了文中。
Q5：既然 Codex 执行强又省 token，混合用两个不行吗？
可以，而且这正是本文框架支持的做法：按任务类型分流——目标明确、验收清晰的任务（正是 Codex 强项，且 SWE-Together 数据里它最省 token：约 29.9k vs Opus 4.8 的 74.0k）交给 Codex；模糊口语需求、长会话持续演进、需要边聊边改的任务交给 Claude 系。真正的错误不是"选了谁"，而是假设"解决率高 = 协作好"，然后用管理执行器的方式去用协作者（或反过来）。
